## 2. 需求分析（商户验证与审批）

### 2.1 整体流程（跨端）

```
商户(App/Web)                      管理后台                          商户(App/Web)
──────────────                    ──────────────                    ──────────────
注册(OTP+条款) ──申请──▶ 入驻中：新线索
                                │ 分配商户运营 / 联系 / 运营评估
                                ├─ 已联系
                                │ 按业务类型分配 KYC 要求 + 发送 KYC 访问/请求
                                ├─ 已授予 KYC 访问权限
                     ◀──KYC 要求── 商户上传 KYC 文件(可草稿/更正重交)
                                ├─ KYC 进行中 → 提交后进入 待验证
                                │ 逐文件批准/拒绝(仅授权验证角色) + 审核进度
                                ├─ 批准 / 拒绝 / 请求重新提交(识别受影响文件+原因)
                     ◀──结果通知──
                     ◀──重交要求── 商户更正/替换文件 → 重新提交队列 → 再审核
                                └─ 最终批准：生成唯一商户访问码
                     ◀──访问码(邮件/短信/App)──
                     ──首次登录：访问码 + 强制 Google Authenticator 2FA 注册──▶
                     ──2FA 设置完成──▶ 访问商户仪表盘
```

商户端申请状态机（PRD 模块 1）：
`注册已提交 → 审核中 → 需要提交 KYC → KYC 已提交 → 验证中 → 已批准 / 已拒绝 / 需重新提交`
（商户端另有草稿态：提交前可保存草稿。）

管理端队列状态机（PRD 模块 11）：
`入驻中(新线索→已联系→已授予KYC访问权限→KYC进行中) → 待验证 → 批准/拒绝/重新提交(→待验证再审)`

### 2.2 核心功能需求清单（模块 11）

**队列与列表**
1. 五个申请队列：入驻中 / 待验证 / 重新提交 / 已批准 / 已拒绝，显示汇总数量。
2. 条件搜索与筛选；全队列分页。
3. 查看公司级信息 + 商户下注册的全部业务（业务类型、城市、业务联系人/手机/邮箱、KYC 状态）。
4. 同一公司/集团可注册一个或多个业务；公司级信息维护一次，业务级信息与 KYC 要求各自维护。

**入驻中（Onboarding）**
5. 分配商户运营；跟踪四阶段：新线索 → 已联系 → 已授予 KYC 访问权限 → KYC 进行中。
6. 记录/更新运营评估；按业务+业务类型选择 KYC 验证要求；发送 KYC 前可预览/管理要求。
7. 发送 KYC 访问/请求；商户运营可协助商户提交 KYC。
8. 商户运营可在入驻期间拒绝/关闭线索并记录原因；内部备注（仅授权用户可见）；完整活动时间线。

**待验证 / 逐文件审核**
9. 查看单个已提交文件；批准或拒绝单个 KYC 文件（仅授权验证角色）。
10. 最终验证决定前跟踪已审核文件数量（门禁：全部强制文件审核通过才可最终批准）。
11. 请求重新提交：识别受影响文件 + 给商户原因/评论；重新提交队列显示进度；新文件与先前验证结果对比审核。
12. 验证完成后批准或拒绝商户申请；已批准只读（文件/验证历史/访问信息）；已拒绝保留受影响文件/原因/审核人/日期/验证历史。
13. 已批准申请不能直接回待验证，除非启动新的重新验证流程。

**访问码与账户安全**
14. 最终批准后生成**唯一商户访问码**；按权限查看/复制/重新发送/重新生成（重新生成使旧码失效，全部审计）。
15. 访问码通过邮件、短信、应用内通知发送。
16. 首次登录必须完成 Google Authenticator 2FA 注册（二维码+手动设置密钥，不过期）后才能访问仪表盘。

**审计**
17. 所有入驻阶段变更、分配、KYC 请求、文件审核、重新提交、批准/拒绝、访问码操作、2FA 重置均入审计。

### 2.3 关键业务规则（提取）

| # | 规则 |
|---|---|
| R1 | 申请必须先进入入驻中队列，才能进入正式 KYC 验证 |
| R2 | 执行入驻活动前必须分配商户运营 |
| R3 | 商户运营可协助提交 KYC，但未经 RBAC 授权不得批准/拒绝 KYC 文件 |
| R4 | 文件级验证操作仅授权验证角色可用 |
| R5 | 最终验证决定前必须审核单个文件（门禁） |
| R6 | 请求重新提交必须识别受影响文件并附原因/评论；先前已接受的文件无需重交（除非特别要求） |
| R7 | 仅当所有强制 KYC 要求均验证成功，申请才能批准 |
| R8 | 被拒绝申请保留拒绝原因/受影响文件/审核人/日期/验证历史 |
| R9 | 已批准申请不可直接回待验证，除非启动新重新验证流程 |
| R10 | 访问码仅最终批准后生成；全平台唯一；重新生成使旧码失效；重发/重新生成受权限控制并审计 |
| R11 | 访问码与 Google Authenticator 2FA 共同用于商户认证；首次登录强制注册，完成后才可访问仪表盘 |
| R12 | 已批准商户添加新物业只需物业级验证文件，商户级 KYC 保持有效（除非业务信息变更或监管要求） |

### 2.4 商户端衔接（接口契约，不实现 UI）

移动端团队需要以下能力，本方案在管理端定义契约并预留数据支撑：
- KYC 文件上传/草稿/提交/重新提交（文件与申请、业务关联）。
- 申请状态查询（审核中/需提交 KYC/KYC 已提交/验证中/已批准/已拒绝/需重新提交）。
- 批准通知 + 访问码下发（邮件/短信/App）。
- 首次登录：访问码校验 + 2FA 注册（设置二维码/手动密钥）+ 2FA 验证码校验。
- 回头登录：访问码 + 6 位验证码（Web 二维码登录为增强项，移动端团队实现）。

## 3. 现状盘点与差距分析

> 现状基于 2026-08-19 代码库实测（含此前按原型实现的 Onboarding/Verify/访问码/2FA 字段等）。

| PRD 需求项 | 现有实现 | 差距 | 整改动作 |
|---|---|---|---|
| 五队列 + 汇总数量 | 入驻(Onboarding)与验证(Verify)分属两页/两套列表，各有统计卡 | 未按“统一五队列”视图呈现 | S1/S2：统一队列 counts + list（tab=onboarding/pending/resubmission/approved/rejected） |
| 公司/集团多业务 | `merchant_application` + `merchant_application_business`（名称/类型/城市/KYC 状态） | 业务级缺联系人/手机/邮箱 | S1.1：business 表补 contact_name/phone/email |
| 入驻四阶段 | stage 1-6（新线索/已联系/KYC已开放/KYC进行中/已通过/已驳回） | 与 PRD 四阶段+终态一致 | 保持，补充“拒绝/关闭线索”审计语义 |
| 分配运营/运营评估/KYC模板/发送KYC/协助提交/内部备注/时间线 | 已实现（OnboardingController 12 接口 + 前端工作台） | 基本满足；KYC 要求“管理”能力弱 | S1.6/S2.3：模板维护/要求预览增强 |
| 待验证逐文件审核 + 进度门禁 | 已实现（doc-review + approve 门禁：存在未核验文档即拦截） | 满足 | 保持，补“强制文件全部通过才可批准”的语义校验（现有仅拦截未审核，需改为仅全通过可批） |
| 重新提交（受影响文件+原因+进度+对比） | 已实现（resubmit 将驳回文档转需重交、revision 对比、进度统计） | “仅受影响文件”粒度可进一步明确；已批准文件保持批准 | S1.4：resubmit 明确受影响文件清单，已通过文件不动 |
| 最终批准/拒绝 | 已实现（approve/reject，9 项预置原因） | 基本满足；拒绝需记录受影响文件 | S1.5/S2.7：拒绝时固化受影响文件快照 |
| 已批准只读/访问信息 | 已实现（approved 详情 + access_code） | 缺少“重新发送”能力 | S1.2：resend 接口 + 审计 |
| 访问码唯一/重生成/重发/渠道 | 唯一生成（MTRP-*）、regenerate、渠道记录 email/sms/inapp | 无重发；无真实发送通道（仅记录） | S1.2/S4：重发接口；真实通知归后续批次 |
| 2FA 强制注册/状态枚举/重置 | 仅 two_fa_* 字段 + 管理端重置 | 无“未注册/活跃/需要重置”状态；无设置密钥生成（供移动端） | S1.3/S2.8：状态枚举 + reset 生成新 secret/二维码契约 |
| 搜索筛选（电话/邮箱/业务名/位置/注册日期） | keyword 匹配名称/信用代码/联系人；无邮箱/电话/业务名/位置/日期 | 部分缺失 | S1.7：搜索与筛选增强 |
| 审计全量 | timeline + activity_log | 缺：KYC 模板变更、访问码重发、2FA 重置（部分有）、协助提交 | S1.8：审计补全 |
| RBAC 职责分离 | 权限键 merchant:verify:doc / merchant:onboarding:* 等 | 需角色分配校验（商户运营不得有 doc 审批键） | S3：角色与按钮键核对 |
| 已批准不可直接回待验证 | 现有 approve 后 status=3，无回退入口 | 满足（无入口） | 保持 + 说明“新重新验证流程”预留 |

## 4. 整改方案（商户验证与审批，管理端+后端）

### 阶段一：数据模型与状态（DB）

| 编号 | 内容 |
|---|---|
| S1.1 | `merchant_application_business` 增列：contact_name / contact_phone(加密) / contact_email / city(已有)；幂等 ALTER，登记 initdb |
| S1.2 | 访问码重发审计：新增 `merchant_access_code_log`（merchant_id/action(generate|resend|regenerate)/channels/operator/created_at）；已有 merchant_info.access_code 保留 |
| S1.3 | 账户访问状态：`merchant_info` 增 `access_status`（0 待设置 2FA / 1 已设置）/ `two_fa_status`（0 未注册 / 1 活跃 / 2 需要重置）/ `two_fa_secret_enc`（加密设置密钥，供注册二维码契约）；`two_fa_last_reset_at` 复用 |
| S1.4 | 重新提交受影响文件：`merchant_verify_document` 增 `resubmit_required_at`（标记本批次需重交时间）；已批准文件不改动 |
| S1.5 | 拒绝快照：`merchant_application` / `merchant_info` 增 `rejected_doc_ids`(JSON，受影响文件快照) |

### 阶段二：后端接口与业务逻辑

| 编号 | 内容 |
|---|---|
| S2.1 | 统一队列：新增 `GET /merchant/verify/queues`（五队列 counts，站点口径）；`verify/list` 支持 `tab=onboarding/pending/resubmission/approved/rejected` 统一分页 |
| S2.2 | 访问码：新增 `POST /merchant/verify/resend-code`（权限 merchant:verify:resend，写 access_code_log + 审计） |
| S2.3 | 2FA：新增 `GET /merchant/2fa/status`（状态枚举）；`POST /merchant/reset-2fa` 增强——置 two_fa_status=需要重置、生成新 two_fa_secret、返回“新注册契约”字段（由移动端消费） |
| S2.4 | 重新提交：resubmit 接口改为仅对标记的受影响文件生效；已批准文件保持批准状态 |
| S2.5 | 门禁语义收紧：`verify/approve` 仅当全部强制文件 status=1（通过）且无未审核/驳回/过期/需重交文件时放行（现有拦截“未核验”，改为拦截“非全部通过”） |
| S2.6 | 搜索筛选：`verify/list`、`onboarding/list` 支持 keyword 命中电话/邮箱/业务名；筛选参数 category/country/city/regDateStart/regDateEnd/status |
| S2.7 | 拒绝快照：reject 时固化受影响文件 id 列表到 rejected_doc_ids；已拒绝详情返回受影响文件+原因+验证历史 |
| S2.8 | 审计补全：KYC 模板变更、发送/重发/重新生成访问码、2FA 重置、协助提交 KYC、拒绝/关闭线索均写 timeline + activity_log |
| S2.9 | 状态守卫：`approve` 后 status=3 的商户，无直接回待验证入口；预留 `POST /merchant/verify/re-verify`（新重新验证流程，本期仅契约） |
| S2.10 | 移动端契约（仅接口定义，不实现）：`POST /app/kyc/upload`、`GET /app/application/status`、`POST /app/auth/access-code`、`POST /app/auth/2fa/setup`、`POST /app/auth/2fa/verify`——文档化字段与状态机供移动端团队对接 |

- [ ] 2FA：状态枚举正确；重置后商户需重新注册（新 secret/二维码契约返回）。
- [ ] 全链路审计：阶段变更/分配/KYC请求/文件审核/重交/批准/拒绝/访问码/2FA 均入日志。
- [ ] 与移动端契约文档化（上传/状态/认证/2FA），接口可对接。
- [ ] `php -l` 全绿 + `vue-tsc --noEmit` 全绿；Docker 冒烟（五队列 → 入驻 → 待验证 → 门禁 → 逐文件 → 批准出码 → 重发/重生成 → 2FA 状态/重置 → 拒绝/重交闭环）。

## 6. 里程碑与风险

### 里程碑

| 里程碑 | 内容 |
|---|---|
| M0 | 方案确认 + 移动端契约对齐（字段/状态机） |
| M1 | 阶段一 DB 落地（S1.1-S1.5）+ 阶段二后端（S2.1-S2.9） |
| M2 | 阶段三管理端 UI（S3.1-S3.8）+ 联调冒烟 |

### 风险与待确认

1. **队列视图取舍**：现有 Onboarding/Verify 分页与五队列统一视图的合并方式（推荐：验证与审批一个入口五 Tab，保留独立入驻页入口或并入）。
2. **移动端契约**：上传/状态/认证/2FA 接口字段需与移动端团队评审定稿（影响 S2.10）。
3. **门禁语义变化**：由“拦截未核验”改为“仅全部通过可批”，会拒绝存在驳回/过期文件的批准——需确认与既有数据兼容。
4. **通知真实发送**：访问码重发/发送暂为记录+契约，真实通道归后续批次。

### 审批流程梳理与重交闭环（2026-08-21）

> 按 PRD《商户验证与审批》（场景 1 / 模块 11）五队列（入驻中/待验证/重新提交/已批准/已拒绝）梳理并补全审批流程闭环。

**流程定义（现状 + 本次补全）**

1. **入驻中**：线索录入 → 新线索 → 已联系 → KYC 访问权限已授予（send-kyc）→ KYC 进行中（confirm）；入驻团队评估/指派运营/发 KYC。
2. **→ 待核实（待验证）**：入驻通过（OnboardingController::approve）创建正式商户 `merchant_info.status=0`，KYC 占位文档迁移挂到商户；此时「待核实」队列出现该申请（`verify/list?tab=pending`）。
3. **待核实内**：逐份文档核验（doc-review verify/reject）；未核验通过的文档会拦截最终批准（门禁）。
4. **→ 重新提交**：文件需更正时 `verify/resubmit`（必填说明）→ `merchant_info.status=6`，已驳回文档转「需重交」(status=5) 并记录 resubmit_required_at；申请进入「重新提交」队列。
5. **→ 回待核实（本次补全）**：商户重新提交文件后，管理员 `verify/resubmit-received`（新接口）→ 需重交文档新增 revision 并回待审(status=2)、`merchant_info.status=0` 回待验证队列。
6. **→ 得到正式认可**：全部强制文档核验通过后 `verify/approve` → status=3，生成唯一商户访问码（MTRP-*）按渠道下发，记录审计。
7. **→ 已拒绝**：`verify/reject`（原因码 1-9 必填）→ status=2，保留拒绝原因/受影响文件/审核人/时间线。

**实现改动**
- 后端：`VerifyController::resubmitReceived`（权限 merchant:verify:resubmit）——校验 status=6、需重交文档全部补齐后：逐文档新增 revision（version+1）+ 回待审 + 清重交标记，商户 status 6→0；路由 `POST /merchant/verify/resubmit-received`。

- **待核实无数据说明**：待核实队列数据来自入驻通过（onboarding approve）创建的 status=0 商户；无此类数据时列表为空属正常，按上述流程产生数据后即有显示。
