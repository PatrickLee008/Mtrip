# 商户注册手机号唯一与联系方式补验整改计划

> 状态：用户于 2026-10-13 授权实施；代码与本机隔离回归已完成，真实渠道与远程验收待完成。原计划日期：2026-10-12。
> 实施记录：[整改实施报告](audits/2026-10-13-merchant-contact-security.md)。用户已清空测试数据，以下存量重复清单保留为历史依据，不再需要逐账号指定归属；未提交草稿固定 7 天规则按授权方案实施。
> 依据：Merchant App PRD v1.0.3 模块 1、已完成的邮箱唯一性整改，以及 2026-10-12 的代码和本机只读数据核查。
> 本轮计划的实施范围：商户服务、数据库、管理后台、Merchant Web 和接口文档。沿用此前约定，不修改 `merchant-app/**` 与 `client-app/**` 源码；Merchant App 后续仅依据接口契约对接。

## 1. 目标和不变项

- 注册手机号与注册邮箱一样，是商户主账号的全平台唯一登录身份；同一账号可管理多个物业。业务、物业和员工资料中的普通联系人电话不参与此唯一约束。
- 注册仍要求同时填写手机号、邮箱，申请人任选短信或邮箱完成初始 OTP；基础注册、KYC、协议、最终批准和首次激活的原有顺序不变。
- 最终批准继续创建正式商户、待激活主账号和首批物业。账号信息优先通过注册时完成真实 OTP 的渠道交付；投递渠道暂不可用时保留待交付状态，不回滚已完成的最终批准。
- 首次激活仍使用访问码或用户名及一次性密码、单次联系方式 OTP、Authenticator。登录后在 Merchant Web「设置与安全」显示两个渠道的真实验证状态，并支持补验。
- 只有经过对应渠道的真实 OTP 才允许将该渠道标记为已验证并开放相应的邮箱／短信登录。后台确认、测试固定码和已投递通知必须与真实验证分开记录。

## 2. 已确认的现状和风险

- 申请草稿现在由 `site_id + registration_phone_index + registration_email_index` 组合定位。换邮箱可复用手机号新建申请；`merchant_admin.mobile_index` 只有普通索引，无法阻止跨商户重复。
- 本机同一个手机号关联未封存申请 2、4、12 及未删除主账号 `m000006`、`m000008`、`m000012`，覆盖站点 7 和 1；另有已封存申请 5、9 和已删除账号 `m000009`、`m000011`。以上是只读核查，不能按时间或状态自行决定号码归属。这三个未删除账号的手机号当前均未标记为已验证。
- 目前注册 OTP 的选定渠道保存在申请 `registration_channel`，正式账号的 `verified_email_at` / `verified_mobile_at` 主要在激活 OTP 后写入；仅看账号字段会漏报注册阶段的真实 OTP 证明。
- 凭证投递已限制为申请的注册验证渠道；短信注册不能直接把凭证改发到未验证邮箱。现有 SMSPoh 接入的是 Verify OTP API，普通账号凭证短信投递会失败；本机只配置了这一条已启用的 SMSPoh 渠道。短信内容投递需核实服务商事务短信接口、凭证权限和模板，再实现独立业务发送能力，不能把凭证塞入 OTP 模板。管理员代录将 email 视作投递渠道，但管理员确认本身不是商户的邮箱 OTP 证明。
- Merchant Web「设置与安全」目前没有联系方式与验证状态，也没有补验操作。其现有账号概要接口没有返回这两个状态。

## 3. 最终业务流程

| 注册路径 | 最终批准时的渠道状态 | 凭证交付前 | 首次激活后 | 设置与安全 |
|---|---|---|---|---|
| 邮箱 OTP | 邮箱已验证、手机未验证 | 已验证邮箱接收账号信息；邮件注明手机号待验证 | 原激活流程不变；若激活使用手机 OTP，则手机也转为已验证 | 仍未验证的手机可发送短信 OTP 补验 |
| 短信 OTP | 手机已验证、邮箱未验证 | 若事务短信渠道已验收，向已验证手机号发送账号信息；否则保留待交付，并通过原手机号 OTP + 收件邮箱 OTP 后改用邮件投递 | 原激活流程不变 | 邮箱仍未验证时可用邮件 OTP 补验 |
| 管理员代录 | 联系信息由管理员确认，真实 OTP 状态仍为未验证 | 先用注册手机号真实 OTP 确认商户；短信内容渠道可用时向该号码投递，否则继续验证邮箱后邮件投递；测试凭证展示不作为真实验证 | 原激活流程不变 | 按真实 OTP 完成情况显示 |

短信内容投递可用时，短信注册无需增加凭证领取步骤。账号短信只发到真实 OTP 已验证的注册手机号，包含访问码、用户名和一次性密码，但不包含激活 OTP；首次激活仍需另行完成 OTP 和 Authenticator。一次性密码设有效期并可安全重新签发，发送日志不记录明文凭证，服务商受理不等同于实际送达。SMSPoh 事务短信能力未经核实，不能仅凭现有 Verify OTP 渠道承诺这条路径已可用。

如果目标环境没有可用的事务短信内容渠道，短信注册的备用领取步骤放在**最终批准之后、凭证邮件之前**。Merchant Web 提供公共“领取激活凭证”入口，申请人凭申请号和原手机号发起，服务端只返回不泄露申请是否存在的通用响应；申请人先重新通过原手机号 OTP，再验证收件邮箱，才向该邮箱投递凭证。发送到未验证邮箱的安全提示不得包含访问码、用户名、一次性密码、商户敏感资料或可直接领取凭证的令牌；邮箱持有人不能单独接管申请。若手机号已失效，走后台审核换绑。

凭证短信或邮件根据投递时的真实状态动态说明，例如“注册邮箱尚未验证，请在设置与安全完成验证”；不能根据收到通知推断另一渠道已验证。发送失败时保留待投递记录、允许幂等重试，不能改投未验证渠道。

## 4. 身份、验证和释放规则

1. **归一化与范围**：注册手机号统一为含国际区号的 E.164 格式，以现有 HMAC 哈希比较；全平台唯一，不按站点拆分。申请与其最终生成的一个主账号可共享同一哈希；不同申请、不同主账号不得共享。普通子账号联系人、物业／业务联系人不占用注册手机号身份；若未来赋予子账号短信 OTP 登录能力，须先纳入统一身份规则。
2. **占用和恢复**：发码前预检，OTP 成功创建草稿、后台代录及最终批准在事务锁内再校验；同站点、同手机号、同邮箱且未形成正式主账号时恢复原申请。不能只凭手机号或邮箱找回申请 token。已批准、停用、注销及普通软删除继续占用；只有留审计的显式释放／换绑才解除占用。
3. **真实验证状态**：注册 OTP 成功时把选定渠道、时间和证明来源持久化；最终批准原样继承到主账号。激活 OTP 或设置页补验成功后，只更新实际完成 OTP 的渠道。测试固定码和管理员确认记录独立来源，生产环境不能作为真实邮箱／手机已验证的依据。短信和邮箱登录仅使用各自已验证且未释放的身份。
4. **未提交草稿的占用期**：建议从草稿创建起固定 7 天，不因反复打开页面而延长；到期后审计封存草稿并显式释放其注册邮箱和手机号，旧注册 token 立即失效。已提交／已批准申请和正式账号不由定时任务静默释放，冲突通过当前已验证渠道 + Authenticator 换绑，或管理员核实后留痕处理。账号里的未验证号码要提示补验或换绑；被释放后保留历史密文，不能继续发 OTP，也不能绕过唯一校验重新激活该号码。具体草稿期限在实施前作为产品规则定稿，不引入后台可配置开关。
5. **换绑**：已登录主账号操作需现有会话、Authenticator、已验证渠道证明及新联系方式 OTP；提交新号码时在同一事务中再次校验唯一性、更新索引、释放旧号码、使相关未用 OTP 和会话失效并记录审计。失去全部已验证渠道的账号走后台身份核验；普通管理员不得直接把验证状态改为已验证。

## 5. 数据、接口与页面设计

### 数据库和一致性

- 采用新增迁移，不改已执行的邮箱唯一性迁移。申请、账号分别增加手机号显式释放字段，以及仅在未释放时生效的全平台唯一键；先跑只读审计并解决冲突，再创建唯一索引。空库快照同步更新。
- 复用现有邮箱占用机制的事务语义，新增手机号排他锁；任何同时写邮箱与手机号的路径固定以“邮箱再手机号”的顺序加锁。唯一冲突转换为现有 `DATA_CONFLICT` 响应；审批冲突不得留下部分商户、主账号或物业。
- 保存注册证明来源／时间、审批后待收件邮箱验证的投递状态和各渠道验证时间。历史密文、哈希、KYC、审核和订单保留。敏感标识只在服务端比较，接口与审计日志输出脱敏值。

### 拟新增接口契约

| 场景 | 契约和权限 | 核心约束 |
|---|---|---|
| 审批后凭证领取备用路径 | Merchant Web 公共领取接口：申请身份确认、短信发码／验码、邮箱发码／验码、读取状态 | 仅在事务短信内容渠道不可用时启用；申请号等仅用于定位，短信 OTP 才签发短期领取票据，随后邮箱 OTP 才触发邮件投递；均限次数、冷却、过期和一次性使用 |
| 设置页状态 | 登录态 `GET /merchant/security/contacts` | 只返回主账号的脱敏邮箱／手机、真实验证状态、是否可补验及原因；跨商户和子账号不得读取或操作主账号身份 |
| 设置页补验 | 登录态对应渠道 OTP 发送、验证接口 | 目标只能是当前账号尚未验证且仍由其占用的联系方式；验证码绑定账号、渠道和联系人哈希，成功后原子更新、记审计 |
| 换绑与人工处理 | 登录态发起换绑及后台审核／释放接口 | 新值先验唯一并完成真实 OTP；后台操作限明确权限、站点范围、原因和审计，不提供无证明的一键“已验证” |

以上为契约草案，实施时沿用 `{code,message,data}`、现有 `ErrorCode`、路由风格和 OTP 限流。Merchant App 只记录同等 API/状态字段的未来对接方式，本轮不修改其页面或请求代码。

### 管理端和 Merchant Web

- 后台入驻详情的最终批准门禁增加手机号冲突原因；明确区分“最终批准已完成、凭证待事务短信／待邮箱验证／待投递、待激活”。审核员可以看脱敏验证来源与时间，不得代商户完成真实 OTP。后台代录保留现有入口。
- Merchant Web 复用现有设置与安全页面，增加主账号联系方式卡：脱敏地址、已验证／未验证／已释放状态、补验入口、换绑说明。成功验证后刷新服务器状态；对子账号只展示其自身可用的安全信息，不提供主账号验证按钮。
- 凭证短信和邮件模板按实时状态写入待补验提醒及设置页路径，不展示 OTP；审批后发往未验证邮箱的安全提示与正式凭证邮件使用不同模板和审计事件。

## 6. 分阶段执行与验收

### 阶段 0：规则定稿与只读审计

- 冻结手机号身份范围、7 天未提交草稿过期建议及已批准但未验证的处理方式。先核实目标短信服务商是否具备可用于生产的事务内容短信接口、凭证与模板；决定短信直投及备用领取路径的上线条件。
- 对所有申请和账号核对手机号密文、哈希、验证来源、软删除、站点与归属；输出脱敏冲突清单和每组建议操作，不更改业务数据。
- **验收**：用户确认重复手机号保留在哪个主账号，以及其他申请／账号的换绑或封存方案；无默认赢家，商户和物业数据不自动删除。

### 阶段 1：模型、证明与占用门禁

- 增加释放和验证证明字段、排他锁、只读审计工具；注册发码、草稿、后台代录、最终批准全部接入手机号占用校验，并保持邮箱现有规则。
- 登录拒绝遗留同手机号歧义，不向不确定账号发 OTP；激活或设置页也不得把有冲突的旧号码标记为已验证。后台显示可理解的占用原因。此阶段迁移只加字段和锁，不创建会被存量冲突阻断的唯一索引。
- **验收**：跨邮箱／跨站点重复、并发申请、同申请恢复、停用／删除仍占用、测试模式不绕过、旧号码验证冲突，以及审批失败零部分写入等隔离用例通过。

### 阶段 2：已验证渠道安全交付与首次激活兼容

- 持久化真实注册 OTP 证明并继承至主账号；邮箱注册向已验证邮箱投递，短信注册优先通过已验收的事务内容短信服务向已验证手机号投递。生产管理员代录先完成真实手机 OTP，不因管理员录入自动获得投递资格。
- 若目标环境不能发事务内容短信，则短信注册及管理员代录保留待交付，通过“原手机号再次 OTP → 邮箱 OTP → 邮件发送凭证”备用路径领取。修正凭证重试和通知文案，一次性密码仅在安全门禁通过后投递，首次激活流程保留。
- **验收**：短信内容投递只发已验证号码，独立于 Verify OTP 且不记录明文凭证；错误邮箱单独持有邮件不能领取或激活；备用路径双 OTP 才发邮件；超时、重试、渠道故障和重复确认幂等；受控收件人确认真实送达。

### 阶段 3：Merchant Web 设置与安全

- 增加主账号手机号／邮箱状态、未验证提示、OTP 补验与必要的换绑流程；API 以服务端主账号范围授权，更新后同步登录方式和审计。
- **验收**：邮箱注册并激活后手机显示未验证；短信 OTP 通过后显示已验证并可短信登录；子账号、跨站点、失效／已释放号码、过期码和错误码均不能修改主账号状态。Web 构建及桌面／移动宽度人工走查通过。

### 阶段 4：存量处理和唯一索引

- 只按阶段 0 经确认的逐条方案执行账号换绑／封存及显式释放；留操作人、原因和时间。尤其核对当前三个未删除账号及已删除测试账号关联的同一号码。商户、物业、KYC 和订单不作推测性删除。
- 审计无冲突且哈希齐全后，执行唯一索引迁移；迁移必须在任何业务表唯一 DDL 前拒绝未解决冲突。迁移后再跑审计和并发用例。
- **验收**：现有库与空库迁移、重复执行、回滚前置核验通过；未获确认的数据保持原样。邮箱和手机号均可在显式释放后重新注册，旧账号不能凭已释放渠道登录。

### 阶段 5：整链路与部署

- 在独立测试库回归邮箱／短信注册、后台代录、KYC、最终审批、短信直投及邮件备用领取、首次激活、设置页补验、邮箱／短信登录以及物业发布；不动真实商户订单或真实联系人。
- 按“目标环境先审计 → 处理该环境冲突 → 迁移 → 商户主池／App 池更新 → 两个 Web 发布 → 健康与真实受控 OTP 联调”顺序部署。每一阶段记录测试和差异，未完成端到端验收前不宣布生产可用。
- **验收**：无重复手机号归属和不明验证状态；SMTP、SMSPoh OTP 及经选定的事务短信服务分别可查日志并由受控收件人确认；无凭证发往未验证联系方式；原注册／激活和酒店发布链路回归通过。

## 7. 实施前需确认的产品规则

1. 注册手机号全平台唯一，包含不同站点和已停用／已注销主账号；物业和业务联系人不受限。
2. 短信注册优先向已验证手机号发送事务内容短信凭证；目标环境未具备该能力时，在原手机号 OTP 和收件邮箱 OTP 后改用邮件交付。管理员代录须先验证手机号；邮箱注册不增加额外前置步骤。
3. 未提交草稿建议创建满 7 天后审计封存并同时释放注册邮箱和手机号；已提交或已批准数据只走明确的换绑／审计释放。
4. 当前重复号码涉及的账号 `m000006`、`m000008`、`m000012`，以及此前已删除测试账号 `m000009`、`m000011`，需要单独指定号码归属和存量处理，不能由迁移自动决定。

用户于 2026-10-13 授权按本方案实施，并已自行清空测试数据。本轮不再执行存量删除或换绑，不发送真实 OTP；目标环境受控收件验收仍需明确接收人。
