## 3. A：推荐奖励异常只读定位

### 已掌握的线索

已查看 `Ref_TC_014.png`：页面显示邀请 2 人、待奖励 1 人、已奖励 1 人，累计奖励却为 **0 MMK**；横幅写有奖励 50,000 MMK。

截图反映“已奖励人数与累计奖励金额不相称”，没有展示钱包余额或流水，单凭该图还不能证明钱包实际未入账。应先核对奖励记录、接口统计和钱包账务，再确定缺陷范围。

当前链路：

- `BookingLifecycleService::checkIn()` → `ReferralService::grantOnFirstBooking()`。
- 站点配置 `referral_reward_inviter` / `referral_reward_invitee` 决定双方金额；缺失按 0 处理。
- `WalletService::credit()` → shared `WalletLedger::credit()` 产生钱包额度批次与流水。
- `ReferralController::my()` 按 `user_referral.reward_amount` 汇总累计奖励；前端两页共享统计数据层。

### 核查步骤

- [ ] 固定 QA 所测环境、前后端版本和实际站点，核对相关迁移是否已执行。
- [ ] 先按截图中的推荐码定位邀请人，查询其推荐绑定，确认哪条记录被标为已奖励；从既有记录补齐被邀请人、订单与时间，不先要求 QA 重新上传证据。
- [ ] 对照 `user_referral` 的 `site_id`、邀请双方、`reward_status`、`reward_amount`、`reward_order_id` 和 `reward_time`，核对关联记录的实际站点归属。
- [ ] 核对订单是否真正经过入住核销，关联入住事件及执行入口；区分只注册、已支付、入住核销和退房。
- [ ] 核对发奖站点双方奖励配置及可取得的变更历史。当前配置不能直接证明历史发奖时配置相同。
- [ ] 查询关联用户、订单的推荐奖励钱包流水和额度批次，核对金额、入账时间、余额快照及是否已消费或过期。
- [ ] 对照推荐汇总/明细接口原始响应与页面，区分数据库金额为 0、接口汇总错误、页面刷新/字段解析错误，以及文案承诺与有效配置不一致。
- [ ] 输出根因与影响范围。现有证据无法定论时，列出确切缺少的业务标识或日志，继续隔离环境复现可确认的分支。

核查账户与日志使用脱敏标识；不把凭据、令牌或完整个人信息写入共享文档。

## 4. B：依据根因实施修复

| 核查结果 | 修复方向 | 处理范围 |
|---|---|---|
| 发奖时站点配置缺失/为 0 | 核实该站点是否应启用奖励，以及应使用的币种、金额和生效范围；纠正目标环境配置/遗漏部署 | 只处理确认的目标站点，不向所有站点统一灌入 50,000 |
| 历史奖励记录已被标为发放，金额为 0 | 形成逐条候选清单，核对历史资格、原始配置和既有流水，单列历史补偿方案 | 修改配置不会自动补发；不直接重置 `reward_status` 或再次核销来补钱 |
| 金额配置正确，但发奖链路异常 | 修复已确认的调用、事务、站点校验或一次性发放问题 | 保持首个合格酒店订单的既定触发时机，单订与 Trip 共用规则 |
| 钱包已有正确入账，推荐统计/页面不正确 | 修复汇总、字段、刷新或显示问题，并核对 Refer & Earn 与 Referral Status 两页一致 | 不重复给钱包入账 |
| 有效奖励配置与固定横幅文案不符 | 明确该站点实际活动规则，修正展示来源或文案 | 不仅改前端数字掩盖实际账务或配置问题 |
| QA 前置条件未满足 | 补齐用例步骤与实际订单状态，再按条件复测 | 未达触发条件不以改发奖时机来满足错误预期 |

### 返利专项验收

| 场景 | 预期与检查点 |
|---|---|
| 有效绑定、站点配置正金额、首个合格酒店入住核销 | 邀请双方按各自配置入账；绑定状态/金额、钱包额度批次和流水能互相追溯 |
| 仅注册、仅支付、入住前取消、无推荐绑定 | 不提前发奖；未满足条件的关系保持既定状态 |
| 同一订单重复核销，或被邀请人再次入住其他订单 | 奖励仅发一次，流水不增加第二笔同类奖励 |
| Trip 多子订单及同一被邀请人的并发核销 | 仅一条关系达成，双方金额不重复入账 |
| 发奖途中发生数据库/钱包异常 | 本次状态与金额变更按事务回滚，不能留下部分入账或提前标为已奖励；恢复后能按既定重试机制处理 |
| 站点不同、币种不同、配置为 0 或缺失 | 配置不串站、不误用其他币种金额；零金额按本轮明确保留或另行确认的规则验收 |
| 历史已奖励但金额为 0，之后补齐正金额配置 | 不自动重复发放；若存在获准历史处置，执行结果可审计且幂等 |
| 已入账后消费或过期 | 累计推荐奖励与实际已发金额一致；可用钱包余额按剩余额度显示，两者不要求相等 |
| 推荐首页、推荐明细和钱包往返/重新登录 | 人数、奖励金额、币种和流水一致，页面刷新拿到实际数据 |

先用隔离数据建立能复现故障的集成回归，再修复并验证上述必要路径；避免只用桩函数证明钱包入账成功。完成专项后执行 README 要求的 `scripts/check.ps1` 质量基线，以及实际改动端的补充检查；浏览器/真机业务验收与构建检查分别记录。
