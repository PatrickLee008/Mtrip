# 客房管理 Figma 与 PRD 整改计划

> 日期：2026-09-16。状态：阶段 0–5 已完成，外部 VR/PMS 集成待服务商条件齐备后单独实施。
> 授权：2026-09-16 用户确认五项决策，要求按阶段推进；不修改两个 App。
> 基线：当前工作区，包含既有未提交的 Hotel Details / Hotel Amenities 实现。它们不是本轮新成果。

## 1. 结论与范围

建议在现有 `hotel_room_type + hotel_room_type_revision` 体系上整改，不重建客房模块。已有基础字段、图片上传、草稿、审核、驳回、历史、复制和停售能力应继续复用。整改重点是原型界面、复合床型、面积单位、媒体三步骤，以及房型配置与库存、订单实际行为的一致性。

拟实施范围为 merchant-web、必要的 goods-service / order-service / shared 后端、admin-web 房型审核、数据库增量迁移和回归测试。沿用用户先前约束，不实现 `merchant-app` 或 `client-app` 功能代码；消费者接口需要保持兼容并验证批准版本，但 App 新媒体播放器与真实终端验收留作独立任务。因此，即便后续 Web/后台阶段完成，也不能宣称 PRD 的移动拍摄与客户交互展示全部完成。

本计划优先覆盖 PRD 模块 2.1 房型管理及模块 2 中直接影响房型的审核、媒体和外部系统边界。酒店政策、增值服务、酒店宣传视频与完整 PMS/Channel Manager 集成记录为模块 2 的关联工作，不隐含纳入本次房型 UI 改造。机场接送按 PRD 属未来阶段。

## 4. 应先处理的现有问题

以下为静态代码发现，实施时先建立失败用例，再修复并回归。

### P0：房型删除无法可靠识别进行中酒店订单

- `RoomController::delete()` 仍按 `order_main.sku_id = room.id` 和旧 `order_status IN (0,1,5)` 检查；新酒店订单使用 `room_type_id`，`sku_id=0`。旧状态集也不包含已入住的 `order_status=2`。
- `RoomReviewService::audit()` 批准删除时直接软删，不复查提交申请之后新增的订单。
- 计划：统一使用 `site_id/property_id/room_type_id` 和业务进行中状态；申请时与批准时都检查，并与下单所持房型锁协调，消除检查后新增订单的竞态。有历史订单的已停用房型仍可追溯。
- 证据：[RoomController.php](../../backend/services/goods-service/app/Controller/Merchant/RoomController.php)、[RoomReviewService.php](../../backend/services/goods-service/app/Service/RoomReviewService.php)、[OrderController.php](../../backend/services/order-service/app/Controller/App/OrderController.php)、[BookingConst.php](../../backend/services/order-service/app/Constants/BookingConst.php)。

### P1：页面物业选择未成为房型写请求的明确上下文

- `api/rooms.ts` 的保存、复制、撤回、停售、删除、上传均未显式传 `X-Mtrip-Property-Id`，由通用拦截器读取全局选择。
- 列表及新增表单有自己的物业选择，且会默认第一家；全局为 All Properties 时，仅 body 的 `propertyId` 不能通过单物业写门禁。全局选 B、页面目标 A 时会受到 B 的范围限制。这是流程阻断风险，不是已证实的数据越权。
- 计划：从正在操作的房型/表单确定物业头；切换物业时清理或确认未保存编辑、重新取列表和统计；保留服务端授权，不放宽 All Properties 门禁。
- 上传还缺少房型/物业归属校验，保存路径仅按月份。新方案应核验目标物业、KYC 和编辑权限，绑定媒体所有权，避免随意引用其他物业文件。
- 证据：[rooms.ts](../../merchant-web/src/api/rooms.ts)、[http.ts](../../merchant-web/src/utils/http.ts)、[MerchantContext.php](../../backend/shared/src/Context/MerchantContext.php)。

### P1：首发库存、周末价和取消政策尚未完全驱动交易

- `launch_stock` 有保存和“不超过 base_stock”校验，但当前读取/下单缺省库存使用 `base_stock`。仅填写首发可售数不会限制初始可售库存。数据库还将 `base_stock` 注释为“基础每日库存”，前端则标作实际总数，需要先冻结含义。
- **[已修复 2026-09-16]** 阶段 2–5 引入 `RoomDefaults::stock()` 把 `launch_stock` 作为无日库存时的默认可售配额，但实现写成 `launch_stock ?? base_stock`。`??` 只在键为 null/缺失时回退，而 merchant-web 新建房型的 `launch_stock` 初值就是 **0**（`RoomEditor.vue` 的 `draft` 初始值，提交校验只查“不超过 base_stock”、不查是否 > 0），因此“填了客房总数、没填默认可售配额”的房型 `stock_total` 被补建成 0，`OrderStockService::lock()` 判定 `available = 0 - 0 - 0 < 1` 抛 `DATA_CONFLICT`(409)「库存不足」；消费者日历（同一函数的另一个消费方）也长期返回 `stock=0`。已改为 `launch_stock > 0 ? launch_stock : base_stock`，0/null/缺失一律视为“未设置”（真正的“不卖”应走停售 `status=2` 或单日 `is_closed`），并在 `shared/tests/cases/SupportTest.php` 补 0/null/缺失/负数回退与周末价回退用例。开发库房型 5 的 `launch_stock` 已设为 40，日历 `stock` 由 0 恢复为 40。**遗留**：无（merchant-web 侧已同轮收口：客房总数变化时自动同步尚未设置的默认可售配额、打开时按客房总数补历史 0 值、提交审核时拦截「客房总数 > 0 而配额 ≤ 0」，详见[模块13](./13-商家端merchant-web落地.md)）。
- 商户日历 `fallbackDay()` 使用周末价；消费者日历无日库存记录时使用基础价；`OrderStockService::lock()` 首次建日库存也使用基础价。周末看见的价格可能与实际下单不一致。
- 房型表单的 `cancellation_policy` 是展示文本；实际订单快照/退款读取 `goods_refund_rule`。选择“不可退款”文本不等于创建可执行的不可退款规则。
- 计划：明确初始配额作用日期/默认值，统一三处缺省库存与报价规则；将取消政策映射到明确的规则 ID/规则结构并冻结订单快照。已有日历覆盖、售出和锁定数量不能被资料审核覆盖。加床价格保留，但加床收费流程另须确认，不能宣称仅存字段就能自动计费。
- 证据：[AvailabilityController.php](../../backend/services/goods-service/app/Controller/Merchant/AvailabilityController.php)、[HotelController.php](../../backend/services/goods-service/app/Controller/App/HotelController.php)、[OrderStockService.php](../../backend/services/order-service/app/Service/OrderStockService.php)、[BookingLifecycleService.php](../../backend/services/order-service/app/Service/Booking/BookingLifecycleService.php)。

### P1：原型币种与当前保存白名单冲突

- 原型为 MMK；前端选项及 `RoomReviewService::normalizePayload()` 只接受 THB/USD/SGD/EUR，不支持的币种会回落 THB。
- 计划：明确站点/物业计价币种，统一保存、展示、库存与订单合同；支持 MMK 时不能只改标签，不能把已有 THB 金额直接标作 MMK。是否支持多币种换算不在原型中得到定义。

### P1：新增交互媒体不能沿用当前弱校验上传契约

- 普通图片上限仅在前端实现；后端保存可接收任意长度 URL 数组，未建立媒体所有权校验。视频时长仅在浏览器校验；`kind` 不是严格枚举，文件主要按扩展名判断。
- 计划：服务端统一检查媒体类型、真实内容、大小、图片分辨率/数量和视频时长；VR URL 仅接受 HTTPS 及确认支持的提供方，嵌入字符串只提取并校验地址，不执行任意 HTML。
- 普通图片不能一律应用 VR 封面的 4:3 规则，360 全景也不能按普通 4:3 图处理。未获批文件不能出现在客户业务接口；是否需要连文件直链访问也受审批保护，应与现有公开上传目录策略一起确认。

### P2：状态、草稿和字段校验需要随新 UI 收口

- 审核状态、房型启停、酒店公开可售应分别显示。`Room Type Status` 不能绕过审批直接发布。状态在修订 payload 和线上表中都有保存，要防止审批覆盖期间的紧急停售。
- `maxGuests >= maxAdults` 目前只有前端检查；床数量、面积、总人数与儿童容量组合需要服务端规则。草稿校验可少于提交校验，避免多步骤未填完无法暂存。
- 详情快照含硬编码英文，展示 `bed_count + bed_type` 时旧床型字符串已带数量，可能重复；撤回状态在列表映射中缺失。新 UI 同时补齐。

## 5. 拟定页面及数据方案

### 5.1 页面与路由

1. `/rooms` 保持客房模块主入口，改为原型卡片列表。Hotel Profile 的 Room Types 页签可进入同一房型能力，避免两套数据和编辑器；原型本身有独立 Room Types 菜单，最终入口组合待确认。
2. 保留 `/rooms/create`、`/rooms/:id/edit`、`/rooms/:id` 直达能力，由同一套列表/详情/四步编辑组件承载。列表打开弹窗，直达路由能够恢复对应内容，不删旧链接。
3. 原型没有画出的复制、删除申请、停售、审核历史放卡片更多操作及详情审核区域，全部沿用原权限。
4. 搜索、筛选、排序在服务端执行；统计对全量授权物业范围聚合，不能对当前一页求和。零房型、超过三种房型、禁用、待审、驳回、加载失败均需有对应状态。
5. 弹窗步骤为 Room Information → Room Images → VR Tour → 3D Floor Plan。下一步仅导航/校验；保存草稿与最终提交审核清晰区分。保留原型主操作位置，补充 PRD 所需的草稿和预览入口。
6. More Details 展示原型图库、参数、设施、VR 与热点；区分“已生效/本次修改/审核历史”。详情里的启停操作必须有写权限并按状态规则保存，不能只是本地切换。

### 5.2 字段与兼容策略（已冻结契约）

| 领域 | 拟定表达 | 旧数据及审核处理 |
|---|---|---|
| 多床型 | `bedding[] = {id, type, quantity}` | 旧 `bed_type + bed_count` 原样转一项；对包含数量的文本不自动拆解；保留旧字段摘要供既有读取 |
| 面积 | 明确数值和原始单位，约定标准平方米值 | 旧值只有纯数值且含义确定时回填；带单位/非数字值列清单人工确认，不静默改值 |
| 设施 | 稳定设施 key、名称、图标，多选 | 复用适用图标资源；旧名称保留；房型设施与酒店 amenities 分开，不能复制酒店页每组 5 项限制 |
| 房间图片 | 媒体引用、分类、排序、封面标记；是否单图启停待定 | `images` 继续输出有效封面在首的 URL 列表；完整媒体元数据随修订保存 |
| 本地全景 | 独立 panorama 类型/元数据、启停、预览 | 不把普通图片当作全景，不与外部导览 URL 合并；新旧版本分别引用 |
| 外部 VR | `enabled, url, cover` | 单独保存、校验和审核；变更前客户继续读批准版本 |
| 平面图 | `enabled, image, hotspots[]`；热点含稳定 ID、归一化 x/y、标题、说明、可选图片 | 坐标按原图比例保存；替换底图时确认重置或重新定位热点；旧数据默认无配置 |
| 早餐/餐食 | 稳定枚举 + 早餐包含关系 | 不把翻译文案当业务值；兼容原有文本，无法识别的不猜测 |

## 11. 2026-09-16 客房列表统计空值修复
