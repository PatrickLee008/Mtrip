## 推荐奖励问题的证据

已查看 `Ref_TC_014.png`：邀请2人、待奖励1人、已奖励1人，累计0 MMK，横幅却承诺50,000 MMK。

通过截图推荐码在用户已有的 2026-11-10 生产双库备份中定位：

| 项目 | 备份中的实际记录 |
|---|---|
| 邀请人 | 用户7015，当时归属站点1 |
| 已处理关系 | 1009：邀请人7015 → 被邀请人7021，站点1 |
| 已处理金额 | `reward_status=1`、`reward_amount=0.00`，关联订单7021 |
| 时间 | 奖励处理于2026-10-27 09:40:58（库内时间） |
| 另一推荐 | 1010仍待达成，金额0，与截图人数对应 |
| 站点配置 | 备份中仅MMK站点5/6/7有双方50,000奖励配置；站点1没有这两个奖励键 |
| 钱包流水 | 该关系关联账户/订单未找到推荐返利入账；普通测试调账不属于推荐奖励 |

因此这不是“已有正金额入账被页面漏加”的证据。备份表明该关系被按零金额处理；固定横幅承诺和“已奖励”人数又让用户误以为已拿到奖励。备份证明的是当时保存的状态；当前配置不能独自证明发放时的全部配置历史。

本轮复用现有 QA 会话，只读查询当前生产推荐汇总及明细：用户7015的会话站点为7，返回1条待达成、已奖励0、累计0，未返回原1009。未据此推断服务器如何处置过旧数据，也未执行生产补偿、修改配置或重新核销。当前原始截图问题主要由历史备份和隔离复现确认，不能声称在当前生产重新复现同一条历史记录。

## 实际修改

- shared 新增 `ReferralRewards::forSite()`，页面所展示与真正发放的金额读取同一站点配置；保留未配置金额为0、不同站点不继承的规则。
- 推荐汇总将正金额计入已奖励人数，额外返回 `noRewardCount` 表示已处理但邀请人未获得金额的历史记录。累计金额保持实际奖励快照汇总。
- 推荐页横幅显示当前配置的金额与币种；未配置时说明本站点没有推荐奖励，旧后端兼容文案不再承诺固定50,000。
- 推荐统计卡解释零金额历史记录；明细第二页签改为“已完成”，零金额记录显示“未发放奖励”，不再显示“奖励已入钱包”或奖励完成进度。
- 发奖前锁定并核对邀请双方账户与绑定的站点、有效账户；不允许把另一个站点的配置写到外站钱包。异常会回滚本次入住操作，避免半笔入账。
- 保留首次酒店入住核销触发、一次性发奖及零金额处理状态，不通过重复核销或直接重置历史状态补钱。没有数据库结构或迁移变更。

API 新增字段为 `program{inviterAmount,inviteeAmount,currency}` 和 `noRewardCount`，原有响应信封与字段保留。App 对新增字段按可选处理，以兼容分批更新。
