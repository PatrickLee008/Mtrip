# 基础注册驳回的队列归属修复

## 需求依据与评估

依据超管 PRD v1.0.19 [M11 商户认证与审批](../../../obsidian/mTrip_obsidian/mTrip%20超级管理后台知识库/03-功能模块/M11-商户认证与审批.md)及 [AC11](../../../obsidian/mTrip_obsidian/mTrip%20超级管理后台知识库/04-验收标准/AC11-商户认证与审批.md)：

- 经授权人员可在入驻阶段驳回／关闭线索，并记录原因；基础注册被驳回后不得进入 KYC。
- “要求修正”与“正式驳回”是不同决定，要求修正仍回到注册审核；已驳回队列保留原因、审核人、日期和活动历史。
- 本次沿用已确认的导航归并（待核实／重新提交常规菜单隐藏），不恢复旧菜单、不修改审批门槛。

**结论：基础注册正式驳回应移入“已拒绝”，不再出现在默认“入驻申请”。退回补正仍在入驻处理。**

根因有两处：`OnboardingController::index` 默认无队列筛选，包含 registration_status=5；`VerifyController` 已拒绝列表／计数只查 merchant_info.status=2，尚未转换的线索根本未进入该表。现有 reject 已正确记录状态、原因和时间线，不应伪造正式商户来补列表。

## 实现范围

- 统一新模型注册驳回（registration_status=5）及旧模型关闭线索（stage=6）的识别。默认入驻列表排除两者，显式 queue=rejected 读取能力保留；普通筛选去掉已驳回选项。
- 已拒绝列表在服务端联合查询正式商户拒绝记录与未转换的已驳回申请，保留原分页／搜索／站点范围；不在浏览器合并两份分页结果。新增 record_type／application_id，row_key 加类型前缀，防止同数字 ID 串行；正式商户来源编号的辅助搜索限定 merchant 类型。
- 导航计数与列表使用相同拒绝范围；成功驳回后刷新侧栏及统计卡。
- 已拒绝申请复用入驻详情侧栏，以 detailOnly 方式只读展示，关闭运营写操作且不额外请求入驻列表／运营候选／旧公共模板。正式商户继续走原详情。
- 验证列表权限 merchant:list:audit 仅可通过详情接口读取本站已驳回且未转换的申请；不能据此读取活跃申请。原 merchant:onboarding:list 保持原范围，无新增写权限或自动授权。
- 仅查询与展示整改，不修改已有申请状态、原因、身份占用、KYC材料或账号；不执行数据迁移，无 SQL 变更。
