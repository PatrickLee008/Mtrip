# 被驳回入驻申请恢复与再次申请

## 用户已确认的范围

用户确认：保留原申请，允许原注册身份显式重新申请；超管可以带原因协助重开；保留各轮提交资料及审核人／时间／原因，已拒绝列表补齐已有超管永久删除入口。删除不是正常重新申请的前置条件。

依据商户App PRD v1.0.14 M01、超管Enterprise v1.0.19 M11与此前冻结契约：PRD未明文要求普通驳回永久封禁邮箱／手机号。此前身份唯一性与rejected终止组合造成原身份不能继续的缺口，本次以用户明确确认的状态扩展修复，不自动释放身份、不产生并行申请。

已批准路径：基础注册rejected → 显式重新开启 → resubmit_required(4) → 修改后submitted(1) → under_review(2) → 经授权批准后才开放KYC。正式商户、已生成账号、KYC拒绝不借该入口重复注册或跳过审核。

### 已实现与独立复核

- App `/application/reopen` 只接受有效原注册token与原applicationId；同手机号／邮箱重新验证仅恢复会话，仍须显式点击“修改资料并重新申请”。失效会话走既有OTP流程；KYC拒绝／正式账号不提供此入口。
- Admin `/onboarding/reopen` 必须isSuper且`merchant:onboarding:reopen`，原因1–200字符、原registrationStatus与stage快照，恢复为补正4，不等同提交／批准。权限20510只为内置超管角色初始化授权，普通管理员即使拿到键也被拒绝。
- 新 `merchant_application_registration_review` 按application_id／round_no唯一；每次正式提交保留公司、注册号、地址、业务及联系人快照，电话保持加密存储，读取按原详情权限解密／脱敏；决定记录保留审核人、时间及原因。下一轮修改不覆盖旧快照。
- 对历史资料只保留当前可知的轮次；旧拒绝在重开前归档，旧补正首次编辑／直接提交、后台注册号更正／评估写入也先归档。历史不存在的更早提交资料无法追溯恢复，不伪造审核姓名。
- 已拒绝列表及详情复用已有超管永久删除双确认。删除连同新审核历史一起清除，释放原身份；常规重开仍保留原申请／手机号／邮箱和业务ID，不创建并行申请。旧模型或身份不完整记录不自动转换为新模型，保留超管核查／删除渠道。
- 后台历史默认收起，旧原因码翻译成人类可读文案。detailOnly拦截模板、文档、审批、注册号等写入口；新增回归使用真实父模板传参验证子组件只读。
- 独立复核修复：App旧实例轮询跨OTP reset覆盖新状态、secondary先点击与重开竞态；后台detailOnly模板编辑遗漏；旧补正无历史时首次写入丢旧资料。全部先失败后通过、定点复核无剩余阻塞。
