# 商户认证测试模式后台运行时开关

## 目标与结论

原测试模式由 `MTRIP_MERCHANT_AUTH_TEST_MODE=true` 直接开启，修改后必须重建服务，测试环境难以由管理员自行启停。现改为部署能力门禁加数据库运行时开关，两者职责分开：部署方决定某环境是否具备测试能力，超级管理员决定当前是否启用。

消费者注册的 `register_sms_required` 继续只控制 Consumer App 注册是否强制短信验证，不参与商户认证测试模式。商户开关独立为 `sys_config.security/merchant_auth_test_mode`，避免关闭消费者强制验证时意外开启商户固定 OTP，也避免开启消费者验证时阻止商户测试。

有效判定为：

```text
APP_ENV 不是 prod/production
AND MTRIP_MERCHANT_AUTH_TEST_ALLOWED=true
AND sys_config.merchant_auth_test_mode=1
```

数据库默认值和部署模板均为关闭。`prod`、`production` 无条件返回关闭，即使环境变量和数据库值均开启也不能接受 `000000` 或展示测试凭证。

## 管理端与运行行为

- 入口：“系统配置 → 全局参数 → 安全配置 → 商户认证测试模式”。开启和关闭均需二次确认。
- 只有超级管理员可保存或通过分组重置该项。非超管即使拥有全局参数编辑权限，后端仍返回 `40301`。
- 部署门禁关闭时，页面禁止从关闭切到开启；若数据库遗留为开启，超级管理员仍可将其关闭。
- 页面显示“测试模式已生效”“允许但未开启”或“当前部署环境禁止开启”，状态来自后端的 `environment_allowed/effective`，不由前端自行猜测。
- 全局参数页的三个布尔安全配置统一渲染为开关与元信息；后台 IP 白名单和注册强制短信验证不再因模板分支错误额外显示 `false` 输入框，商户测试模式仍额外显示生效状态标签。
- 生效后，商户注册、激活、登录和恢复的邮箱/短信 OTP 使用固定码 `000000`；仍要求先创建 challenge，并保留过期、重发冷却、错误次数、一次性使用、站点和账号绑定。
- 最终批准跳过 email/sms 外部凭证投递且不伪造成功，inapp 仍按原流程处理；超级管理员可查看尚未激活账号的加密凭证。
- 最终批准在请求开始时读取一次有效模式，并将同一值传给实体创建结果和凭证投递，避免审批过程中切换开关导致响应与投递不一致。
- 全局参数批量保存先校验全部配置，再在同一连接事务中写入；同批次存在非法或不存在的配置时，测试模式不会部分落库。

## 变更与部署

- 新迁移：`V20260918120000__add-merchant-auth-test-toggle.sql` 新增 `merchant_auth_test_mode=0`；`V20260918121000__add-global-config-reset-permission.sql` 补齐既有 `config:global:reset` 的菜单权限键，使后端注解、菜单种子和前端 `v-perm` 对齐。
- 新部署变量：`MTRIP_MERCHANT_AUTH_TEST_ALLOWED`，已透传主池和 APP 池；旧变量 `MTRIP_MERCHANT_AUTH_TEST_MODE` 退役。
- 修改部署变量后必须执行 `cd deploy && ./mtrip.sh start` 重新创建容器；`restart` 不会加载新的 Compose 环境。
- 数据库开关是运行时读取，后台开启或关闭后无需重启 merchant-service。

本地开发环境已设置部署门禁为 `true`，便于后台测试；迁移后数据库开关保持默认关闭。发布到测试环境时也必须显式设置部署门禁并重建服务。生产环境应保持门禁为 `false`，同时由生产硬锁提供第二道保护。
