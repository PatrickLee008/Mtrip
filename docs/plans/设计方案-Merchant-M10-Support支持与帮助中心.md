## 2. 已确认的产品决定

| 编号 | 已确认规则 | 适用范围 |

| 既有位置 | 开发前能力/缺口 | 复用与补齐 |

| system-service `Admin/HelpController.php`、`help_category/help_article` | 平台 FAQ 内容源；商户尚未接通，文章列表不含正文 | 读取现有数据，增加商户可见性与详情查询，不直接开放管理接口 |
| merchant-service `Admin/PlatformRuleController.php` 与合规服务 | 真实政策版本、违规、警告和不可改写审计 | 新增商户只读投影，沿用生效版本与商户例外规则 |
| merchant-service `Merchant/NotificationController.php` | 通知、个人已读、受控跳转；现有通用通知授权不足以涵盖工单隐私 | 为 Support 通知增加专属访问条件和深链校验 |
| `MerchantContext::authorizedPropertyIds()` | 当前通用查询限定酒店 | Support 局部使用跨受支持业务物业授权，不能直接把酒店集合作为全部资源 |
| `MerchantImpersonationGuard::allowed()` | 代为登录为显式只读白名单 | 工单写操作保持拒绝，平台人员从平台工单入口回复 |

**服务归属设计：**工单两端控制器都放在 merchant-service，调用同一 `SupportTicketService`；工单、回复、事件、附件和站内通知都使用该服务的业务库 default 连接。FAQ 经现有 system 连接只读查询；指南由独立适配器读取外部服务。无需新增微服务或跨服务复制工单。

平台接口使用 `/api/v1/admin/merchant/support/*`，沿用现有 `merchant → merchant_service` 网关映射；商户接口使用 `/api/v1/merchant/support/*`，仅新增 `support → merchant_service` 映射。原 `/admin/help/* → system_service` 保留，平台页面按功能使用对应 API。

## 5. 页面与交互

### 5.1 路由与布局

- `/support` 默认工单页；`tab=tickets|faq|compliance` 和 `ticketId` 用于刷新恢复及受控深链。过滤条件可保留，页面本地草稿不得跨账号复用。
- 工单首页沿用 Figma 的浅底、白卡、蓝色主按钮、胶囊标签；复用项目已有字体/令牌，不整体重做 Header、物业选择器或访客消息导航。
- `/support/guides` 为唯一指南模块，系统侧栏 User Guide、Support 内指南入口及顶部常驻“指南”均进入该路由；不是新增一套内容管理功能。
- 平台新页 `/helpcenter/merchant-tickets`，菜单 component 为 `helpcenter/merchant-tickets/index`，采用项目现有列表/抽屉/权限模式。
- 1440/1280px 验证主布局；375px 验证筛选换行、卡片堆叠、全宽抽屉/弹窗和表格可操作，不机械缩小桌面稿。

### 5.2 查询、创建与详情

- 工单列表：关键词匹配工单展示号或主题；分类、优先级、六状态筛选；默认 `updated_at DESC, id DESC`。查询变化回第 1 页，普通分页沿用 `page/pageSize`。
- 汇总卡按当前站点、商户/物业和授权范围统计，不随关键词或列表状态筛选消失；点击汇总卡应用对应状态集合。四卡之和等于该范围工单总数。
- 创建：固定七个初始分类码覆盖结算打款、预订、技术、供应定价、评价、客房、其他；与 FAQ 分类分开。低/中/高三级优先级。元数据由后端返回，前端不维护另一套枚举，本期不增加分类维护页面。
- 单物业上下文自动带入实际所属商户与物业；All Properties 下先选择一个授权商户，再选择“商户通用”或一个授权物业。集团不能用 `merchant_id=0` 创建归属不明的工单。
- 工程初始限制：主题 200 字符、描述 10000、回复 5000；均拒绝超限而非静默截断。单次最多 5 个附件，每个不超过 10MB（10,000,000 字节），客户端显示与后端一致的实际字节上限；字符数、附件个数和 MB 字节口径是实施默认值，不标为 PRD 数字。
- 创建成功返回唯一展示号并打开详情，刷新汇总和列表；失败保留输入，结果不明时保持原 requestId 重试。取消有改动的草稿时提示确认。
- 详情分别分页读取回复和活动历史，展示真实创建/更新时间及平台客服；未指派显示“未指派”，不填原型姓名。
- 非终态允许授权员工协作回复，不限制必须是创建者；上传成功后可单独补充附件，空文字且无附件禁发。终态必须先显式重开，不能通过发送接口自动重开。
- 切换物业/商户时取消旧请求，清空失去授权的选中项；迟到响应不得覆盖新上下文。深链带物业提示时先核验、再恢复上下文并重取详情。

## 6. 状态流转与一致性

内部状态码建议为 `open/in_progress/waiting_merchant/waiting_support/resolved/closed`；显示文案与 C04 一致。

| 动作 | 允许的源状态 | 目标状态/行为 | 操作者 |
| --- | --- | --- | --- |
| 创建 | 无 | open | 商户 create |
| 商户回复/补附件 | 四种非终态 | waiting_support | 商户 reply |
| 客服回复 | 四种非终态 | 默认 waiting_merchant；可明确选择继续 in_progress 或 resolved | 平台 reply；选择 resolved 还需 status 权限 |
| 指派/转派 | 非终态 | 首次指派 open 可转 in_progress；其他状态保持 | 平台 assign |
| 调整优先级 | 非终态 | 状态保持，写历史 | 平台 priority |
| 标记处理中/等待 | 非终态 | 显式目标；waiting_support 不表示伪造商户发言 | 平台 status |
| 解决 | 非终态 | resolved，必填处理说明 | 平台 status |
| 关闭 | 非终态或 resolved | closed，必填原因 | 商户 close 或平台 status |
| 商户重开 | resolved/closed | waiting_support，必填原因 | 商户 reopen |
| 平台重开 | resolved/closed | 有有效客服则 in_progress，否则 open，必填原因 | 平台 reopen |

四种非终态之间不允许直接传入任意状态绕过动作接口。已关闭不能重复关闭；重复相同请求返回原结果，不新增历史或通知。重开不删除解决/关闭事件；原客服失效时清空当前指派并记录原因，历史署名不改写。

所有工单写操作使用 `requestId`；已有工单还要求 `expectedVersion`。事务内锁定工单、复核当前身份/权限/归属，写回复或变更、递增版本、追加活动，再写必要站内通知及幂等结果。唯一键兜底并发创建及重试。相同请求不同内容返回冲突；版本冲突提示刷新，不能覆盖新数据。业务异常使用现有 ErrorCode 常量和统一响应，不假定所有冲突都表现为 HTTP 409。

客服停用或权限移除后保留历史，但不再是可操作指派对象；候选客服必须有效且能访问该站点工单。没有自动派单、定时关闭、超时升级或外部通知任务。

## 7. 权限、数据范围与通知

### 7.1 权限设计

| 商户权限 | 用途 | 平台权限 | 用途 |
| --- | --- | --- | --- |
| `mch:support:list`（已有） | 入口、汇总、列表、详情、授权附件读取 | `help:ticket:list` | 平台工单列表、详情、附件与候选客服查询 |
| `mch:support:create` | 创建/创建时上传 | `help:ticket:reply` | 对商户回复及附件 |
| `mch:support:reply` | 进行中回复/上传 | `help:ticket:assign` | 指派/转派 |
| `mch:support:close` | 关闭 | `help:ticket:priority` | 调整优先级 |
| `mch:support:reopen` | 重开 | `help:ticket:status` | 处理中、等待、解决、关闭 |
| `mch:support:merchant-scope` | 商户通用工单及商户级合规信息 | `help:ticket:reopen` | 重开 |
| `mch:support:guides` | 统一指南入口/查询 | 既有 FAQ/合规权限 | 保留原发布、处置权限，不由工单权限替代 |

权限名为拟定契约；商户写权限落 `04-merchant-menu.sql`，平台权限落 `02-menu.sql`，与后端注解及 `v-perm` 同键。新权限不批量授予旧员工角色，主账号遵循现有账号类型及权限机制；即使拥有全部动作权限也仍需资源授权。

### 7.2 资源规则

- 服务端从当前有效账号确定 site、商户集合、角色和物业范围；工单相关操作重查实时授权，不只信任旧 JWT。平台超管按 `AdminContext::scopeSiteId` 语义全平台查询，其他平台人员强制本站点。
- Support 授权查询包含受支持业务物业，不按酒店专属字段过滤；限定站点、主体、员工分配与软删除，不用营业状态撤销历史工单访问权。账号本身无权登录时继续遵守现有访问门禁，不另开绕过入口。
- 仅在 Support 路由为中间件注入对应授权集合；其他业务尤其访客消息的授权保持原有语义，不能为此全局扩大范围。
- 物业工单：当前账号必须有该物业授权；门店账号仅本门店。商户通用工单：仅集团/商户账号且具备 merchant-scope 权限；门店账号即使为主账号也不可读取。集团须选定其范围内的真实商户。
- 单物业列表只展示该物业工单；通用工单通过 All Properties 下的通用筛选访问，避免显示为某家物业的问题。跨业务未定义的交易字段不展示酒店入住信息。
- 商户级违规/警告暂无可靠物业归属，按 merchant-scope 展示；不能因员工拥有一个物业就暴露全商户合规详情。关联违规工单保留同样访问约束。
- 附件、回复、时间线、统计和深链均继承父工单授权。跨站点/商户/物业猜 ID 不返回主题、正文、文件名或数量侧信道。

### 7.3 通知与更新

复用 `merchant_notify`、投递记录及个人已读表，新增受控 `support_ticket` 深链类型，目标为 `/support?ticketId=...`。只保存必要摘要；发送时确定有效接收人，读取列表、统计、标已读、清理、destination 和点击后详情都再次约束工单权限，不能仅校验 merchant_id。

平台回复、补充信息请求、指派相关更新、解决/关闭/重开等按事件 ID 去重通知；平台设置处理状态的可见变化同样进入历史与通知。商户自身操作不向操作者重复投递；平台工单队列可从真实数据获取更新，本期不增加外部坐席提醒渠道。

工单写入、活动和必要站内通知在业务库同一事务完成；投递记录失败回滚，避免回复成功但缺少必要通知。现有通知发送服务不能直接带商户 AdminContext 调用平台管理路径，需在 Support 服务内复用同库数据结构并明确事件写入口。

同步以共享数据库为事实源：动作成功立即重取详情/汇总，页面重新获焦刷新；可见页面每 15 秒增量检查更新，失焦/离开停止，失败显示重试状态。PRD 对工单要求同步更新，首期不新增 WebSocket；不要把聊天实时传输需求套用到工单。通知已读不改变工单状态。

## 8. 数据与接口设计

### 8.1 最小数据模型

以下表名/字段为实施草案，正式迁移需结合当时结构和命名校验；不分配猜测的菜单 ID 或迁移编号。

| 数据表（业务库） | 核心字段/约束 |
| --- | --- |
| `merchant_support_ticket` | id、唯一 ticket_no、site_id、merchant_id、可空 property_id、category、subject、原始 description、priority、status、created_by、assigned_admin_id、version、可空 violation_id、created_at/updated_at/resolved_at/closed_at |
| `merchant_support_reply` | ticket_id、actor_type/id/name 快照、content、created_at；仅追加；创建描述保存在主表，不复制为两份可编辑原文 |
| `merchant_support_event` | ticket_id、动作、前后状态/优先级/客服、操作者、原因、version、时间；仅追加，作为活动/审计依据 |
| `merchant_support_attachment` | ticket_id/reply_id 或短期 upload_token、归属账号/站点/商户/物业、私有存储键、原文件名、检测类型、字节数、状态/时间；成功绑定后不可转绑其他工单 |
| `merchant_support_request` | site_id、actor_type/id、request_id、payload_hash、ticket_id、result_json；唯一约束保证幂等并区分不同身份域 |

展示号由服务端唯一序列生成，采用 TK 前缀，日期/序列格式在实现中固定并加唯一索引，不复用订单号生成器、不更改任何订单编号。列表索引覆盖 site/merchant/property/status/updated_at/id；回复、事件按 ticket_id/id 分页；按实际查询补索引，不增加搜索引擎。

不引入删除工单或编辑既有回复接口。临时附件在事务提交时绑定；失败/取消保留待清理状态，按短期过期清理未绑定对象，不删除已引用文件。存储复用已有私有附件机制的基础能力，但使用独立 Support 记录、存储目录和授权；不得公开静态 URL。

文件校验包含实际类型与扩展名、大小、上传者与上下文；XLSX 识别为受支持的表格文件，不能把任意 ZIP 当 XLSX。下载采用受控流及安全文件名，富文本/文件名不能形成脚本执行入口。

### 8.2 商户接口草案

统一前缀 `/api/v1/merchant/support`；写入参驼峰，列表行沿用 snake_case；成功 `{code:0,message,data}`，普通分页 `data={list,total,page,pageSize}`。

| 方法与路径 | 用途/关键参数 |
| --- | --- |
| GET `/options` | 授权商户/物业、分类/优先级/状态、附件规则及当前动作能力 |
| GET `/summary`、`/tickets` | 授权汇总；keyword/category/priority/status/page/pageSize，额外通用/物业范围筛选 |
| GET `/ticket` | ticketId；原始请求、元数据、版本和当前允许动作 |
| GET `/replies`、`/events` | ticketId + 分页；支持 afterId 增量同步 |
| POST `/create` | requestId、授权 merchantId/propertyId、category/priority/subject/description、attachmentIds、可选 violationId |
| POST `/reply` | ticketId/requestId/expectedVersion/content/attachmentIds |
| POST `/close`、`/reopen` | ticketId/requestId/expectedVersion/reason |
| POST `/attachments/upload` | 创建上下文或已存在工单；按 create/reply 权限检查，不允许提交时伪造上传者 |
| GET `/attachments/download` | attachmentId；重新核验当前父工单/临时归属与读取权 |
| GET `/faq/categories`、`/faq/list`、`/faq/detail` | 只读已发布 merchant/all 文章，分类可见，当前站点或全平台内容 |
| GET `/compliance/summary`、`/rules`、`/violations`、`/warnings`、`/appeals` | 真实合规投影、搜索筛选、关联申诉工单；均在 `/compliance` 子前缀下 |
| GET `/guides/categories`、`/guides/list`、`/guides/detail` | 外部指南适配；契约核验前不宣称已可用 |

### 8.3 平台接口草案

前缀 `/api/v1/admin/merchant/support`：GET `/tickets`、`/summary`、`/ticket`、`/replies`、`/events`、`/assignees`；POST `/reply`、`/assign`、`/priority`、`/status`、`/reopen`、`/attachments/upload`；GET `/attachments/download`。

列表支持工单号/主题、商户、站点（仅超管）、分类、优先级、状态、日期筛选。平台不代表商户新建工单，不增加批量处理或自动派单。写操作使用相同版本/幂等协议；`/status` 只接受本方案状态矩阵中的平台动作。

## 9. FAQ、合规与指南细化

**FAQ：**保留现有管理源；按文章与分类的站点、发布状态、受众和软删除共同过滤，详情再次检查；隐藏分类不计入数量，空分类不显示原型假数量。内容正文安全渲染。没有数据时引导创建工单，不自动编写政策答案；多语言缺内容时沿用真实原文并标明，不伪造翻译版本。

**合规：**只取当前生效发布快照并应用商户例外，绝不返回草稿、未来未生效正文、全量例外商户名单或内部备注。违规保持发生时规则修订引用，警告采用既有撤销/到期投影。无计分规则返回 null/未配置，0 只表示已配置规则下的真实零值。

**关联申诉：**按 C11 从商户可见的违规入口创建关联工单，提交材料及原因，复核时展示原违规引用；警告保持真实展示。以工单状态表达“咨询/申诉处理进度”，不把 resolved 自动显示为“申诉获批”，也不把 closed 显示为“申诉驳回”。正式处罚复核结果、扣分撤销和账户恢复仍由合规域处理，本期不增加自动联动。待处理申诉卡仅统计该授权范围关联违规的非终态工单，并明确为工单口径。

**指南：**运营维护始终在外部集中指南中心。已只读核对 PRD 指向的公开 API 文档 `https://guide-hub-production-m6ybjs.laravel.cloud/docs/api#/`，Client API 1.0.0 使用 `/api/v1/app`、分类和视频指南接口，鉴权为 `X-App-ID`/`X-App-Secret`；服务端校验 app ID 与商户 slug 后提供最小投影。没有登录外部后台或使用 PRD 凭据；真实已发布商户内容、语言/站点范围及媒体观看仍未联调。账号/凭据不复制入方案、仓库配置样例、前端构建或日志。

已实现服务端 HTTPS/超时/禁重定向、分类分页、搜索/详情投影及鉴权/限流失败状态。待配置 `MTRIP_GUIDE_HUB_APP_ID`、`MTRIP_GUIDE_HUB_APP_SECRET`、`MTRIP_GUIDE_HUB_MERCHANT_SLUG` 后，用真实商户内容继续核验受众/语言/站点定向及媒体访问方式。密钥只在服务端；不把外部后台管理登录页当商户观看入口，不以 C 端 `app_tutorial` 替代。

2026-10-27 按用户指定 Figma 用户指南模块补齐 Web 页面：首页按真实分类取两条预览，分类“查看全部”与全局“全部视频”进入同路由列表，后者保留未分类/历史分类内容的访问；搜索和分类使用 URL 条件，支持刷新/返回恢复与分页重试。卡片显示标题、分类及接口提供的适用功能。服务端仅补充格式校验后的 YouTube `video_id`，客户端据此生成缩略图及点击后加载的隐私增强播放器，保留外链观看；关闭详情/切换查询时取消旧请求并忽略迟到响应。公开契约无时长字段，因此不填原型示例时长。无数据仍为空态，未配置/限流/服务失败/详情失败如实提示。已完成隔离组件与媒体专项、本机发布及质量基线，真实商户内容/播放验收 A12 继续保留未完成，详见[本轮验证](./audits/2026-10-27-merchant-support-local-rollout.md#用户指南对齐-figma)。

外部 401/403、超时、无内容分别给出真实状态与重试；密钥刷新和播放链接有效性按服务契约实现，不猜测接口。若服务缺少必要能力，只暂停指南相关联调，记录缺项，工单/FAQ/合规独立推进；指南验收仍保留未完成，不把空壳算交付。
