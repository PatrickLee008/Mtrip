## 1. 目标与范围

为酒店商家提供访客消息工作台，覆盖住客入住前、在住和离店后的沟通。商家能在查看预订上下文的同时收发消息、记录内部事项、分配负责人并结束本次处理。

本方案以用户提供的 Figma `guest-messaging` 为界面依据，以新版 Merchant PRD v1.0.8 的 §10.2–10.7“住客消息”及相关验收标准补齐业务规则。本次确认的首期范围为商家 Web 工作台 + 消费者端聊天闭环，并兼容 `merchant-app` 现有订单消息入口；商户 App 独立完整消息工作台安排在下一阶段。这是用户确认的交付顺序，不代表新版 PRD 将商户 App 排除在产品范围之外。

新版“概述”及“组合与业务领域管理”明确将住客消息列为所有受支持业务领域共享的商户功能。因此，产品入口与会话归属不能限定为酒店专属。当前提供的画布和 §10.2–10.7 的具体上下文以酒店为主，本方案细化酒店会话；餐厅等已支持业务应保留共享入口及物业范围，按实际业务展示可用信息。尚无餐厅聊天原型和预订上下文定义的部分列为待补规格，不套用酒店房型、入住状态或虚构餐桌预订流程。

本期“访客”明确为已登录的消费者；未登录先登录，已登录但尚未下单的用户可以咨询酒店。商家与消费者的酒店会话、消费者与平台客服的会话、商家向平台提交的支持工单是三条不同业务链路。本次设计重点是第一条，不将平台客服消息混入酒店列表。

第 9 节的 9 项产品规则及正文对应内容已由用户确认；其余仍标注“建议”的内容是工程设计依据。第 1–10 节保留需求与设计基线，实际实施和验证以第 11 节为准。

Figma 标为 Module 11，新版 PRD 正文仍将住客消息放在 Module 10 下，因 §10.1 已单列支持工单，住客消息编号为 §10.2–10.7。本文 M11 仅是对应 Figma 的工作名称，不代表新版 PRD 新增了“模块 11”。

支持工单与住客消息必须分开解读：§10.1 的六类工单状态、超级管理后台同步、附件设计参考 PDF/JPG/PNG/XLSX 和最大 10MB，明确属于商户向平台寻求帮助的工单。§10.4 对住客聊天只明确“图片和文档”，没有规定同样的扩展名、大小或六状态流程；住客附件参数现已由用户单独确认，见第 7/9 节，不能把工单参考值当作聊天硬性要求。

新版未直接确定的匿名访客、售前线程粒度、个人/团队未读、已解决后自动重开、快捷回复维护方式和内部备注版本规则，现已按用户确认的推荐方案固定，见第 9 节；这些规则的依据是本次产品确认，不追溯表述为 PRD 原文。内部备注与三个快捷回复入口来自 Figma，而非 §10.2–10.7 的明文条款。技术考量说明 API、数据模型和基础设施在实现阶段由工程协作确定，因此第 6 节方案不视为 PRD 指定架构。

| 能力 | 当前证据 | 对本次设计的影响 |

## 4. 页面与交互方案

### 4.1 总体布局

保持原型的“现有商家导航 + 会话列表 + 聊天内容”三段结构。页面内容区实际为左右两栏，不增加常驻右侧住客档案栏或顶部 KPI 卡片。

- 现有左侧导航增加 Guest Messages / 住客消息（本方案沿用原任务名“访客消息”），作为跨受支持业务领域的共享入口，沿用全局物业选择器；未读角标只统计当前可访问范围。
- 会话列表建议宽 300–360px，含 Messages 标题、搜索、原型三个胶囊页签与可滚动列表。该宽度是响应式建议，不是已读取的 Figma 精确值。
- 聊天区按“会话头部 → 预订摘要 → 内部备注提示 → 消息历史 → 快捷回复 → 输入框”排列；历史区独立滚动，头部和输入区固定。
- 采用原型白色背景、浅色分隔线、蓝色商家气泡、浅底访客气泡、绿色已解决、橙色内部备注。使用现有字体和主色令牌，对图时再核对具体字号与尺寸。
- 桌面双栏展示；窄屏改为列表/会话单栏切换，进入会话有返回按钮，返回保留筛选与滚动位置。建议验收 1440、1280 和 375px，不将桌面原型机械缩小。

### 4.2 会话列表

每行包含头像/姓名缩写、访客名称、房型或“售前咨询”、最后一条对客消息摘要、时间、未读数和 Resolved 标签。在 All Properties 范围中增加酒店名，以免同名访客或跨酒店会话混淆。

建议排序为最后一条对客消息时间倒序、ID 倒序作为稳定次序；内部备注、查看和分配不把会话顶到最新。访客有未读时姓名/摘要加粗。姓名缺失用本地化兜底，不能展示原型假人名。

搜索支持住客名、真实订单号、酒店名，服务端分页查询，输入防抖。All 展示当前授权物业范围内的受支持会话；Unread 为当前员工尚未读的访客消息；In-House 只用于酒店，以真实预订的 `booking_status` 在住状态判断，不凭日期推断，非酒店上下文不展示此酒店专属筛选。额外筛选提供新版规定的“待处理 / 已解决”，内部建议映射为 Open / Resolved；未读仍是独立读取维度，可与处理状态组合。未分配 / 分配给我是补充的界面筛选建议。

### 4.3 会话头部与预订上下文

头部显示访客姓名、入住提示、会话处理状态和负责人。更多菜单提供新增内部备注、分配/转交、标记已解决/重新打开。不同操作按权限控制。

预订卡展示真实订单号、酒店/房型、入离日期、晚数/人数、支付状态、订单金额与币种，点击跳到已存在的预订详情。All Properties 下必须能识别所属酒店。没有订单的售前咨询只展示酒店和“尚未关联预订”，不填示例金额或自动绑定最近一笔订单。

预订摘要的字段和跳转继续检查原模块权限：能访问聊天不自动获得完整预订编辑权或敏感财务数据。订单金额/支付信息按已授予的预订字段权限展示，收益、佣金、结算和打款等受限信息不因聊天上下文而暴露。其他业务领域使用其已定义的上下文，不显示酒店入离日期或房型。

入住时间提示由服务端按物业业务时区生成；物业未配置时区时需要采用已明确的站点时区规则，不能分别由浏览器和容器 `date()` 猜测“明天”。预订支付状态、入住状态和会话解决状态相互独立。

电话按钮沿用 `mch:order:guest-contact` 的授权与审计语义，有权限且有有效号码才能获取明文并打开 `tel:`。售前会话不能因没有订单就绕过联系方式权限。站内语音通话不属于本次图标的默认实现。

### 4.4 消息区与输入区

- 保留访客左侧、酒店右侧气泡与发送时间；酒店方可显示员工署名，平台介入显示独立身份。
- 首屏取最新一页，向上加载历史；用户阅读旧消息时收到新消息，显示“有新消息”提示，不强制滚到底。真正停留底部才自动跟随。
- 输入框支持多行、Enter 发送、Shift+Enter 换行，中文输入法组合输入期间不触发发送。移动端有明确发送按钮。
- 文本建议上限 2000 字符，前后端一致；超限提示而不是静默截断。空白消息禁发。
- 消息状态为发送中、已发送、已送达、已读、失败。失败保留原内容和重试入口，重试使用原 clientMessageId 防重复。
- 快捷回复固定显示原型中的入住时间、Wi-Fi 信息、路线三个入口。点击后填入可编辑草稿，再由员工发送；不直接对客自动承诺。
- 快捷内容按物业及语言维护。入住时间和路线可引用已维护的酒店资料；Wi-Fi 密码仅对可证明有权限的在住订单提供，无资料时提示配置，不编造密码、路线或提前入住承诺。
- 图片先缩略图再预览；PDF 显示文件名、大小和下载。上传中、失败、取消有明确状态，上传完成后才能提交附件消息。

### 4.5 内部备注

沿用原型“新增弹窗 → 橙色入口 → 查看/编辑面板”。按钮明确标注“仅酒店员工可见”，颜色与普通消息区分。保存不会调用对客发送接口，也不触发访客未读。

已确认首期为每个会话一份可编辑的当前备注，记录最后修改员工、时间与版本；编辑保留修改历史，并用版本号防止两个员工互相覆盖。原型未明确要求多条工单式备注流，暂不增加该界面。取消编辑不覆盖原文。

有订单时，消息备注与订单备注分别保存，各自明确用途，不自动同步或双写。

### 4.6 空态与异常

明确覆盖首次无消息、搜索无结果、未选择会话、加载失败重试、会话已失去访问权限、附件不可用、连接中断和已解决后继续咨询。切换物业必须取消旧请求/订阅，清空不在范围的选中会话，防止迟到响应展示上一家酒店内容。

## 5. 核心业务规则（产品规则已确认）

### 5.1 会话粒度

| 场景 | 已确认的会话粒度 | 规则 |
| --- | --- | --- |
| 酒店详情发起售前咨询 | site_id + property_id + user_id + order_id=0 | 同一用户同一酒店复用售前线程 |
| 预订详情发起或商家 Message Guest | site_id + property_id + user_id + order_id | 同一订单复用同一线程；多订单不混聊 |
| 平台在线客服 | 原 type=2 规则 | 继续独立，不出现在商家酒店工作台 |

消费者登录账号是当前可验证的通信身份；预订联系人姓名可以展示，但不能把姓名/电话号码当作聊天授权依据。没有关联消费者账号的线下/外部订单明确提示“该订单暂不支持站内消息”，保留已有受控联系方式入口，不自动创建消费者账号或发送短信。

售前会话后续下单时不自动合并历史，售前与订单线程保持独立；同一消费者的不同订单也分别建立会话。

### 5.2 状态分开管理

| 维度 | 含义 | 不应出现的耦合 |
| --- | --- | --- |
| 会话待处理 / 已解决（建议内部 Open / Resolved） | 员工是否认为本次问题已解决 | 打开消息不能自动标记已解决 |
| 当前员工未读 | 当前员工尚未查看的访客消息 | 同事查看不应消除我的个人未读 |
| 团队待回复 | 最新对客交互为访客发言且尚未解决 | 已读不等于已经回复 |
| 预订 Pending / Confirmed / In-House 等 | 履约真实状态 | Resolved 不改变入住、付款或退款 |

已确认 Resolved 是可恢复的处理标记：访客新发言自动重开，员工再次发送时也先原子重开；原线程保留全部历史，不另建会话。Figma 已解决态仍保留输入区。现有 type=2 平台客服的“结束后禁发”语义保持原约定；酒店 type=1 的旧 finish/send/start 路径在后续实施时需一并调整并回归，不能只修改商家页面。

### 5.3 未读与收件确认

每个员工独立保存访客消息的已读位置，消费者保存酒店消息的收件位置和已读位置，均只能单调前进。新获授权员工可以查看授权范围内的历史，授权前消息不计为其个人未读；授权前已存在的团队待回复状态不因新增员工而被清除。

只有会话前台可见、消息已加载且阅读到对应位置时才发送 read；获取列表、后台预取、只收到推送不能标为已读。页签失焦后不自动清未读。在 Unread 页签打开会话后，允许当前已选会话暂时留在视图，刷新列表时再退出，避免内容突然消失。

“已发送”表示服务端持久化成功；“已送达”表示至少一个接收端实际确认取得消息；“已读”表示接收方提交有效阅读位置。WebSocket 事件已发出或站内通知已写入，都不能单独证明送达/已读。

### 5.4 员工协作

首期采用手动认领、主管分配和转交；不增加轮询派单或复杂排班。候选员工必须当前启用、同站点且有该物业和消息处理权限，转交前服务端重新检查。

负责人用于明确责任，同物业有回复权限的同事可以协作回复，不限制只有负责人能回。分配/重开/解决记录操作者与时间，修改使用版本检查，冲突时提示刷新。员工停用或失去物业授权后不能继续接收订阅或处理，应回到未分配待处理范围。

### 5.5 消息通知

访客消息到达后更新列表摘要、当前员工未读和侧栏角标，并生成可深链到具体会话的站内通知。已分配会话通知负责人；未分配则通知有处理权限的当前物业员工。员工自己的发送和内部备注不触发访客新消息提醒。

已确认首期提醒范围为站内通知、未读角标和页面实时提醒。事件按 messageId 去重；页面正在阅读该会话时不重复弹提示，声音由用户选择。本期不包含关闭网页或 App 后的浏览器/手机系统推送，也不包含邮件、短信或 WhatsApp；后续如扩展这些渠道，再单独定义需求与验收。

对齐新版 §6.1/6.3/6.5：通知应进入现有通知历史，带相关物业、时间和会话深链，并遵循已配置的通知偏好。通知“已读”和聊天“已读”独立，点击“全部通知已读”不能消除未查看的聊天消息。

## 6. 数据与接口方案

### 6.1 数据扩展

复用既有聊天表，建议新增或补充如下信息，具体 DDL 在实施前结合存量数据确定：

| 数据 | 最小补充信息 | 目的 |
| --- | --- | --- |
| chat_conversation | 明确 property_id；处理负责人、解决操作者/时间、并发版本 | 可授权、可协作、可追踪 |
| chat_message | 具体 sender_id / sender_role、client_message_id、附件引用 | 区分员工/平台、幂等、防伪造 |
| 会话参与者读取记录 | 会话 + 身份 + 接收/已读位置 | 个人未读与真实回执 |
| 会话内部备注及版本 | 会话、正文、编辑者、版本、时间 | 仅内部可见和并发保护 |
| 附件记录 | 会话、上传者、存储键、类型、大小、状态 | 会话内授权和上传归属 |
| 物业快捷回复 | 物业、语言、类型、正文、启用状态 | 不把样例回复写死在前端 |
| 操作审计 | 分配、转交、解决、重开等事件 | 交接与问题追溯 |

会话初始化采用业务唯一键和数据库冲突处理防止并发重复创建。消息发送以“会话 + 发送身份 + clientMessageId”唯一约束去重，事务内落消息、更新摘要/会话状态，提交后才通知。内部备注正文不进入 last_message。

酒店旧 target_id 不能直接复制到 property_id：优先从 order_id 对应订单回填物业；无订单的历史记录只能使用有证据的旧商品到物业映射。不能确定的保留原记录并列为待核对，不猜测、不删历史、不对商家暴露未知归属。先做只读数量与映射报告，再设计可回滚迁移。

### 6.2 建议接口

商家接口统一为 `/api/v1/merchant/chat/*`；以下是设计草案，不是现有 API：

| 接口 | 用途 |
| --- | --- |
| GET conversations | 授权范围内列表，关键词/原型页签/处理状态/负责人筛选 |
| GET conversation | 会话头部、预订上下文、当前权限与读位置 |
| GET messages | 分页历史与 afterMessageId 增量补拉 |
| POST start | 按已授权订单定位/创建，兼容订单 Message Guest |
| POST send | 发送文字/已上传附件，必须带 clientMessageId |
| POST received / read | 接收端确认与阅读位置 |
| POST resolve / reopen | 改处理状态并记录审计 |
| GET assignees；POST assign | 仅列有资格员工，认领/分配/转交 |
| GET note；POST note | 内部备注读取与带版本保存 |
| GET templates；POST templates/save | 读取/维护物业快捷回复，维护需单独权限 |
| POST attachments/upload；GET attachments/download | 会话内上传和受控读取 |
| GET unread-summary | 当前员工在当前授权范围的未读消息/会话数 |

使用项目统一 `{code,message,data}`；普通分页保持 `data={list,total,page,pageSize}`，消息查询额外支持按消息 ID 增量定位。请求参数驼峰，响应保持项目已有约定。现有 `/merchant/order/guest-thread`、`guest-message` 保留路径及权限，内部转调相同收发逻辑，避免旧抽屉漏更新未读/通知。

消费者沿用 `/app/chat/*`，补充明确的 propertyId / orderId、附件、回执和增量读取。客户端传入 orderId 时必须验证订单属于当前消费者并归属该物业；客户端不能自行指定 site_id、发送员工或会话所有者。兼容旧参数前先确认实际调用与版本，不继续扩大 targetId 的歧义。

### 6.3 服务归属与实时通信

建议聊天接口继续由现有 user-service 承载，新增 MerchantAuthMiddleware 保护的商家 chat 分组，并在网关注册 merchant chat 上游；订单域负责授权预订入口与提供上下文。跨旧订单入口、C 端和平台坐席收敛一份核心消息写入逻辑，避免每个控制器独立维护消息、读位置和事件。无需新建独立微服务。

正式实时交付建议采用 HTTP 上传/发送/历史读取 + WebSocket 事件通知：数据库为事实源，现有 Redis 只承担实例间广播。主池和 APP 孪生池均须参与广播；断线后通过消息 ID 补拉并重取会话/未读快照，不能把 Redis Pub/Sub 当可靠历史队列。只做前端轮询可作为试运行阶段，但须明确标注它未完成 PRD 实时要求。

连接使用经过鉴权的短时连接票据，不把长期 JWT 放到 URL；订阅前验证会话与物业范围，权限撤销/退出后及时失效。增加网关 Upgrade、超时、连接限流与健康检查。客户端重连不重复提交消息，发送持久化成功但事件广播失败时仍可由补拉恢复。

## 7. 权限与隔离

商家读取条件统一为“当前站点 + 当前账号授权物业集合 + 当前选择范围”；All Properties 仅代表授权集合，不是全平台。单物业携带正数 `X-Mtrip-Property-Id`，全部物业不传 `0`。请求、订阅和下载每次核验资源归属。

物业停业不撤销已有的商户消息授权，仍允许有权限的员工处理历史会话；账号/角色/物业授权撤销及物业软删除继续阻止访问。消费者新建售前咨询仍须通过营业与发布状态检查。实时连接遇到明确的登录失效或权限拒绝时停止重试，切换账号/物业后重新核验；临时网络错误可继续重试。（2026-10-16 权限缺陷修复）

现有 `MerchantContext::authorizedPropertyIds` 的数据库回退路径只查询 hotel 物业。酒店阶段继续沿用已验证的范围；落实新版跨业务共享入口时，需先核对中间件注入集合及各业务授权来源，为受支持业务明确范围，不直接删除 hotel 条件扩大其他模块权限。角色/物业范围为空时应拒绝访问，不能退回整个商户集合。

对齐新版 §7.3 的完全访问、受限编辑、仅查看、无权限四级访问：只读员工可按授权看会话但不能发送、改备注、分配或解决；受限编辑允许哪些操作由角色模板明确；无权限员工不显示入口且接口拒绝。具体消息权限键是工程映射建议，不在本任务重新创建一套员工角色体系。

建议独立权限 `mch:chat:list/send/resolve/assign/note/template`，订单入口保留 `mch:order:message`。旧入口的兼容授权明确按入口处理，不因有订单消息权限就自动扩权到所有独立消息功能。菜单种子、后端 `#[Permission]` 与前端 `v-perm` 同键，沿用现有服务切面注册约定。管理员聊天保留 AdminContext 站点范围，不以商家身份绕过物业授权。

新菜单建议路由 `/guest-messaging`、component `guest-messaging/index`，页面目录对应 `merchant-web/src/views/guest-messaging/index.vue`。这是本方案建议命名，实施时应先检查菜单是否已有保留路由。

已确认首期附件白名单为 JPG/JPEG、PNG、WebP、PDF；图片每张 ≤10MB、PDF 每份 ≤20MB，单次最多 5 个附件。文件按内容检查 MIME，禁止可执行内容和路径穿越；只能发送本人上传且绑定该会话的附件。附件采用私有存储并通过鉴权接口读取，不直接复用可公开访问的 `/uploads` 目录。访问失效或失权后不可继续下载。

上述参数来自本次用户确认，不是新版 PRD 明定的上限，也不套用 §10.1 支持工单的 XLSX/10MB 参考规则。后续实施前核对平台现有附件配置并与本规则对齐，不静默更改已确认的类型和上限。

## 8. 交付阶段与验收

阶段是实施顺序，不是把 PRD 要求默认为可省略。完整上线需要阶段 1–4 全部完成；如果只授权先交付文字试用版，要在状态中明确标出图片/文档、回执和实时等未完成项。

此处完整上线指第 9 节确认的本期酒店 Web + 消费者端范围；商户 App 独立消息页和其他业务上下文不计为本期已完成内容。目前阶段 0–3 的源码与隔离联调完成，阶段 4 的本地环境发布已于 2026-10-16 完成；正常账号收发复验与原生设备验收待完成。

| 阶段 | 工作 | 验证标准 |
| --- | --- | --- |
| 0. 决策与基线 | 规则及实施已获授权；旧会话只按明确的订单/站点/用户映射，不猜测歧义 target_id | 可说明每类旧会话如何归属、哪些记录不能自动迁移 |
| 1. 会话与授权基础 | 物业归属、唯一键、核心发送、个人读位置、旧入口适配 | 并发创建不重复；跨物业/跨站点/冒用订单全部拒绝；旧抽屉能收发同一线程 |
| 2. 页面及消费者文字闭环 | 主界面、筛选、上下文、备注、分配、解决/重开、C 端真实入口 | 双真实账号来回发消息、分页回看、刷新保留；各状态与原型对齐 |
| 3. 完整通信能力 | 附件、快捷回复维护、实时事件、送达/已读、站内通知 | 跨主池/APP 池及时可见；断线补齐无重复；接收确认后才变送达；附件越权下载失败 |
| 4. 回归与发布 | 数据迁移演练、构建/类型检查、真实浏览器及移动设备验证 | 旧订单入口/平台客服回归通过；文档标明真实设备和推送是否已验 |

关键验收用例：

1. 集团可跨已授权酒店查看；员工只看其物业；切换物业时迟到响应不会串酒店。
2. 售前无预订可咨询；同一用户不同订单保持独立；线下无用户订单给出明确限制。
3. All / Unread / In-House 与处理状态组合筛选正确，同名访客和酒店名可检索。
4. 两名员工独立未读，A 阅读不清除 B 的个人未读；阅读不等于团队已回复。
5. 消费者已读后商家回执更新；应用在后台或只收到事件时不误标已读。
6. 重试同一 clientMessageId 只生成一条消息；断线重连后顺序、摘要和角标一致。
7. Resolved 新消息按已确认规则重新打开，不丢历史；取消/退房不自动删除会话。
8. 备注、修改历史和员工联系方式不会出现在任何消费者接口、附件元数据或订阅事件中。
9. 无资格员工不能接收转交；撤权后实时连接、列表和附件访问均失效。
10. 快捷回复使用正确物业/语言；无 Wi-Fi 或无在住权限时不能泄露密码。
11. 图片/PDF 真上传、预览/下载成功；伪造 MIME、超限、外部 URL、他人附件及跨会话引用失败。
12. 1440/1280/375px 无主要内容溢出，长中英文、输入法、输入区与移动键盘可用。
13. 跨受支持业务领域保留消息共享入口；酒店 In-House/房型/入离日期不套给非酒店业务，缺少业务规格的上下文明确列为未完成项。
14. 仅查看员工不能发消息/改备注/分配/解决；聊天权限不越权读取预订、佣金或结算信息。
15. 通知在现有历史可查并能跳入相应会话；仅把通知标为已读不会清除聊天未读。

各验收用例实际覆盖见第 11 节及实施报告；浏览器移动视口不等同于原生真机或软键盘验收。
