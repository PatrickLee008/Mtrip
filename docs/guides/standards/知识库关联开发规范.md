# 知识库关联开发规范

## 1. 适用范围与协作边界

本规范为开发助手关联需求提供流程。共享知识库位于代码仓库的 `obsidian/mTrip_obsidian/`，笔记、原始快照与附件随 Git 版本管理。Obsidian 是可选的阅读工具，不是项目启动、开发、测试、提交或 CI 的前置依赖；没有安装 Obsidian 也可直接阅读 Markdown，知识库不可用时继续使用项目原有需求来源。

- 涉及功能、业务规则、接口行为或验收的任务，先定位本次需求依据，再分析当前代码；有可用本地知识库时按下文关联阅读。
- 不涉及业务需求的纯工程任务，无需查阅知识库或增加需求映射表。小修复按实际需要记录几行即可。
- 不要求安装或启动 Obsidian、安装插件、创建/同步仓库、挂载目录或获取他人的本地资料。
- 不在应用配置、依赖安装、构建脚本、Git hooks 或 CI 中增加知识库前置检查。共享内容只在 `obsidian/mTrip_obsidian/` 维护，不额外复制；个人 Obsidian 配置、回收站和系统文件由 Git 忽略，不在项目指令中固化个人绝对路径。
- 缺失、不可读或没有相关模块时，直接回退，不因本地库缺失申请额外文件权限、反复重试或等待配置。

## 2. 项目知识库定位与回退

仅对需要查阅需求的任务进行一次有界定位，路径相对于代码仓库根目录解析，不使用当前子目录猜测路径：

1. 本次任务明确要求不使用本地库时，直接使用项目原有来源。
2. 本次任务明确提供知识库路径时，只检查该路径；否则若当前进程已设置 `MTRIP_KNOWLEDGE_ROOT`，只检查该值。
3. 两者均未提供时，检查约定位置 `<仓库根目录>/obsidian/mTrip_obsidian`。该目录随项目共享，不再依赖仓库外的 `documents/` 目录。
4. 候选目录中的 `00-mTrip 产品知识库.md` 可读时，按相关产品继续定位；目录、入口或所需笔记不存在/不可读时，使用下面的回退来源。不搜索整个磁盘或用户主目录，也不自动创建目录。

`MTRIP_KNOWLEDGE_ROOT` 只是开发助手的可选定位覆盖，不是应用运行参数。不要求成员设置，不修改 shell 启动文件，不写入 `deploy/.env` 或前端 `.env`；也不通过执行配置文件来加载它。未指定路径覆盖时，独立 checkout、Git worktree、Windows 或远程环境均使用各自仓库内的约定位置，不复用其他成员的个人路径；若此前设置了旧路径，应取消或更新该覆盖。

成员取得包含知识库的项目版本后，可直接阅读 Markdown；使用 Obsidian 时，选择“打开文件夹作为仓库”，打开 `obsidian/mTrip_obsidian/`，不要在其中再次创建同名目录。不需要社区插件、Obsidian Sync 或额外同步服务。个人配置由 Obsidian 在本机生成，不提交。具体入口见[知识库使用说明](../../../obsidian/README.md)。

回退时先读取本次任务提供的需求与已确认方案，再按需查找仓库内的 `设计文档/`、`docs/reference/`、对应的 `docs/plans/` 和任务指定的设计稿。先列出现有文件、核对版本，不根据历史记录猜测文件名或默认提取文本为最新版本。

本地库缺失本身不是任务阻塞项，不应要求用户补建知识库；如需说明，一句“本次依据仓库内 PRD/已确认方案”即可。只有实际需求缺失或存在影响实现的歧义时，才提出具体问题，并继续不依赖该问题的工作。

## 3. 产品与条款定位

从知识库总入口进入相关产品，不一次性加载全部笔记：

| 产品 | 知识库内相对入口 | 常见代码范围 |
| --- | --- | --- |
| 消费者 App | `mTrip 消费者 App 知识库/00-知识库首页.md` | `client-app/` 及相关后端服务 |
| 商户 App / Web | `mTrip 商户 App 知识库/00-知识库首页.md` | `merchant-app/`、`merchant-web/` 及相关后端服务 |
| 超级管理后台 | `mTrip 超级管理后台知识库/00-知识库首页.md` | `admin-web/` 及相关后端服务 |

按任务读取相关模块/子模块、业务流程、模块内验收、文末验收汇总及相关待澄清事项。支付、预订、库存、促销、钱包、通知、审核等跨端业务，按关联索引查看确实受影响的其他端，不因此扩大本次实现范围。引用时同时标明产品与模块编号，避免将不同产品的同号模块混用。

专题索引用于导航；业务依据需要回到对应原文摘录，必要时核对 `08-原始资料/` 的完整快照。整理发现、术语说明和“待澄清事项”不视为已批准的新需求。

## 4. 版本基线与冲突处理

- 本次明确确认的需求变更，记录确认内容、适用范围及被替代条款；不能推广为所有模块或后续任务的统一变更。
- 本次任务指定了 PRD 版本或已确认方案时，以该基线定位资料。未指定时，沿用对应模块已确认的团队基线；不能因为本地存在更高版本就自动升级任务基线。
- 同一任务无论是否有本地知识库，都应遵循同一已确认基线。知识库版本与任务基线不同或无法核对时，只用作导航和差异参考，实际需求回到基线原文；不能用本地版本覆盖团队依据。
- 开始时核对相关笔记的 `prd_version`、来源和引用条款；使用摘录行号前核对其完整快照。需要判断源 PRD 是否更新时，可对照源文件与导入记录的版本/哈希；不把一次性导入当作实时同步。
- PRD、设计稿、计划或跨端条款存在分歧时，列出来源、版本和对本次任务的影响。已经明确确认的范围可以继续；会影响实际业务行为的未确认分歧先澄清，不自行裁定。更高版本、更新日期或当前代码行为均不单独构成裁定依据。
- PRD 状态、规划进度和历史交接中的“已完成”不证明当前实现或上线完成；仍需检查代码、权限、数据范围及测试/运行证据。

例如，若 `设计文档/` 内商户端 PRD 是 v1.0.8，而共享知识库是 v1.0.12，应明确版本差异；只有任务已确认采用 v1.0.12 时才据此改变业务行为。将知识库移入代码仓库不等于升级所有模块的需求基线。

## 5. 开发与验收记录

涉及业务变更时，在现有模块计划或任务记录中简要说明产品、PRD 版本、章节/条款、本次范围及跨端影响；有库时附原文摘录入口，无库时引用可用的原 PRD 或已确认方案即可。不要要求其他成员使用个人知识库链接才能理解需求。

复杂任务可使用以下表格；简单任务可用等价的几行文字，不额外创建重复文档：

| 需求依据(产品/版本/条款) | 当前实现与缺口 | 本次处理 | 验证证据或待验项 |
| --- | --- | --- | --- |
| 原 PRD、方案或确认记录中的具体条款 | 已满足/缺失/不一致/未验证，并列代码位置 | 修改范围或保留原因 | 对应测试、页面检查、未验原因 |

核对需求相关的前端流程、API、权限、站点/物业范围、状态流转与数据记录。按变更执行项目已有质量基线和必要的专项验证，不用“构建通过”代替业务验收，也不因知识库不可用而跳过原有检查。

任务完成后按项目已有要求更新对应模块计划、README 进度与 HANDOFF，记录需求依据、实际变更、测试结果及未验项。影响团队判断的新决策或需求差异应写入仓库内可共享的任务记录，不能只留在本地知识库中；不把完整 PRD、图片或个人路径复制进进度日志。

## 6. 知识库更新边界

普通开发任务只读取本地知识库；不自动修改原文摘录、原始快照、导入清单或手动批注。当前规范不包含自动同步、索引服务或写回机制。

任务明确包含 PRD/知识库更新时，再按版本差异更新，保留历史来源和人工整理内容，核对受影响的摘录、验收与跨端索引。共享内容的修改通过项目原有 Git 提交与评审流程交付，其他成员更新项目版本即可获取，不依赖个人同步服务。历史导入记录中的原机器路径只用于溯源，阅读与开发使用库内原始快照和相对链接，不要求其他成员复现这些路径。普通开发任务中知识库不存在时，完成仓库侧任务记录即可，不把补建或写回知识库作为交付条件。

## 7. 场景验收

| 场景 | 预期行为 |
| --- | --- |
| 项目内存在可读的约定目录 | 读取总入口及相关条款，核对任务基线后用于开发与验收 |
| 已取得项目知识库但未安装 Obsidian | 直接读取 Markdown，开发与验收流程不受影响 |
| 未配置环境变量且约定目录不存在 | 直接使用本次需求及仓库资料，无需安装或创建任何内容 |
| 显式路径不可读、入口缺失或只有部分产品 | 回退受影响部分，不提权、不无限重试、不阻止无关工作 |
| 本地版本新于团队任务基线 | 明示差异，不自动改用新版规则；需要变更时记录任务确认 |
| 其他 checkout、worktree、远程环境或 CI 无本地库 | 原有开发、构建、测试与提交入口保持可用，无本地库依赖 |
