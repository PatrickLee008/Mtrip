# QA7014 站点迁移被通知阅读记录拦截的恢复

适用错误：`20261119073300` 迁移失败，日志包含 `QA7014: unreviewed dependency in merchant_notify_read`。

`merchant_notify_read` 是 `(notify_id, account_id)` 主键的无站点阅读关系表，包含已读和隐藏时间。原迁移漏掉该关系的保留规则，正常阅读记录触发未知依赖检查。原隔离测试未构造阅读记录，此次已补齐并先复现相同错误。

该错误发生在原迁移的业务备份/更新循环前。原始 SQL 的异常处理会回滚业务事务；备份表和辅助存储过程等 DDL 可能保留。仍需用下列检查确认实际状态，不能删除阅读记录来绕过检查。

## 服务器操作

在项目根目录获取本修复，使用原部署维护窗口和数据库容器配置：

```bash
git pull --ff-only
bash scripts/recover-qa-merchant-7014-site.sh --check
bash scripts/recover-qa-merchant-7014-site.sh --apply
bash scripts/db-migrate.sh --status
```

各步成功后，在 Ops 中重新执行“自动发布”。`--check` 默认只读；`--apply` 会执行指定商户迁移和带审计的账本恢复。容器名不同时设置 `MYSQL_CONTAINER`，其余仍使用标准双库及容器中的 root 凭据；无需把密码写入命令或文档。

恢复命令执行流程：

1. 核对原版本为 failed，原 SQL 路径及 SHA-256 与失败账本一致；保留原文件及校验和。其他未完成版本、未应用或校验不符的前置迁移会阻断。
2. 核对6个核心对象仍在站点1且没有已提交的原始行备份；若上一恢复已提交业务数据但未完成账本，必须6个对象都在站点7且6份核心原始备份齐全。混合状态拒绝自动处理。
3. 将双库（含存储过程、事件、触发器）完整备份到 `deploy/backups/qa7014-recovery-*.sql`，另存SHA-256。备份失败时不执行修复，备份文件按私有权限创建。
4. 获取标准 `mtrip_schema_migrations` 数据库锁，复核状态，在独立新版本 `V20261119090000__recover-qa-merchant-site-notification-reads.sql` 下执行修正逻辑。
5. 新版本验证阅读关系表的已知字段及复合主键，保持阅读/隐藏记录和无站点投递回执不变；仅迁移原清单中商户/通知等有站点的记录。保留订单、资金、共享资源及未知依赖检查。
6. 修正版成功且核心对象、原始备份再次核对后，在同一账本事务中保存原失败行的完整JSON快照及此前恢复失败快照，记录新版本真实校验和/执行者/双库备份路径，并将原意图记为由新版本完成。原行的校验和、原attempt_id及Git来源保留，`applied_by` 标记 `recovered-by:20261119090000`；新版本记录自身真实执行。

原始失败证据保存在 `mtrip_system.schema_migration_recovery.original_ledger`，正常的迁移校验、Ops发布和MySQL健康检查继续使用既有账本规则，无需 `--skip-db` 或删除历史版本。该恢复不是把未执行的业务变更直接标为成功。

## 失败与重复执行

- 修正版的业务前置检查或事务失败时，原 failed 状态保留；新版本记录 failed，业务修改和行备份回滚。完整双库备份保留，检查具体错误后再处理，不能仅反复点击发布。
- 若修正版业务数据已提交但账本事务中断，重新执行会验证6对象及其备份，幂等完成账本，不重复增加账号认证版本。若仍为 running，需人工确认未有执行进程，命令不会自动覆盖运行状态。
- 两个版本都已记录完成时，重复运行不再改业务数据、账本或创建备份。
- 修复已在其他环境完成、原版本为 applied 而新版本未执行时，走普通发布流程；新版本对已迁移或目标不存在的环境幂等跳过。

完成后用消费者站点7确认 Test Hotel（7522）的列表、详情和库存；商户账号重新登录，原密码和已绑定认证器保留。通知的阅读/隐藏状态应继续保持。目标服的实际恢复和最终可见性仍需执行后确认。
