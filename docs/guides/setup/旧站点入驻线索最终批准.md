# 旧站点入驻线索最终批准兼容修复

## 原因与处理方式

适用提示：`新商户统一归属站点7，请先迁移旧站点的入驻申请`。

新建入口已统一站点7，旧线索仍保留原来的站点。此前的 `20261119073300` 与其修正版
`20261119090000` 只迁移已批准商户7014及其已列明的关联数据，不包含尚未转成正式商户的其他申请。
因此之前创建的“测试公司”等旧线索即使KYC完成，最终批准仍会被站点校验拦截。

2026-11-20 修复将兼容处理放在超级管理员最终批准的原有事务内：

1. 已完成批准的幂等请求直接返回原结果；已存在正式实体或状态异常的申请不进入迁站逻辑。
2. 对未转成正式商户的旧申请，核对目标站点7启用、关联记录归属一致、没有其他申请或正式物业
   交叉引用；站点专属公共KYC模板不能被自动扩展到另一站点。
3. 将本申请、全部注册业务、KYC文件及版本、文件审核事件、内部备注、签署记录、时间线和本申请
   的私有物业KYC模板一起迁入7。公共模板、公共条款和系统上传文件记录保留原ID及归属；文件不重传。
4. 写入 `onboarding_site_migrated` 时间线，记录原站点、目标站点、操作者；然后继续原KYC／协议／
   邮箱手机号唯一性和最终批准检查，创建站点7的正式商户、主账号及首批物业。
5. 任何检查或落库失败，迁站、迁站审计及实体创建整体回滚。成功重试不会重复迁站或重复建商户。

该处理仅由具有原审批权限的超级管理员最终批准触发，不自动批准其他旧线索，不迁移已有正式商户。
同一公共条款的既有签署继续有效；若站点7使用不同的生效条款，本次自动处理会整体回滚并明确
要求先单独迁站再重新签署。旧申请在原站点重新签署仍是原站点条款，不能靠反复提交解决；
此类情况需另行核对目标条款和完整关联数据后执行专门迁移。源站点专属公共模板或混站数据
同样返回具体冲突，需先核对，不能绕过审批门禁。

## 测试服发布与重试

本次无数据库结构变更、无新增SQL迁移，不需要手工批量更新 `site_id`。
本轮同时提供只含后端服务修改的 `mtrip-legacy-onboarding-approval.patch`，无需等待Git提交即可由运维
上传到服务器 `/tmp/mtrip-legacy-onboarding-approval.patch` 后按下面步骤发布。
同时提供 `mtrip-fix-legacy-onboarding.sh`，内容为下方备份发布脚本，可上传到 `/tmp/` 后在仓库根目录执行。
若已通过正式提交同步本次修复，则不重复应用补丁，按原发布流程更新商户双池即可。

在服务器仓库根目录先检查既有迁移状态：

```bash
bash scripts/db-migrate.sh --status
```

若仍存在 `20261119073300` 或 `20261119090000` 的失败账本，先按
[QA7014迁移恢复指南](./qa-merchant-7014-site-recovery.md)恢复。本站点兼容修复不修改这两份历史SQL，
不跳过失败账本，也不需要再次执行已完成的7014业务迁移。

确认账本正常后，安排短暂商户维护窗口，暂停其他自动部署，再备份和发布：

```bash
bash <<'BASH'
set -euo pipefail
umask 077
legacy_migration_preview="$(bash scripts/db-migrate.sh --dry-run)"
printf '%s\n' "$legacy_migration_preview"
if printf '%s\n' "$legacy_migration_preview" | grep -q '^  PENDING  '; then
  printf '本修复没有新增SQL。请先核对并完成现有待执行迁移，再发布此补丁。\n' >&2
  exit 1
fi
git apply --check /tmp/mtrip-legacy-onboarding-approval.patch
bash deploy/mtrip.sh stop merchant-service merchant-service-app --prod
mkdir -p deploy/backups
legacy_site_backup="deploy/backups/before-legacy-onboarding-approval-$(date -u +%Y%m%d-%H%M%S).sql"
docker exec "${MYSQL_CONTAINER:-mtrip-mysql-1}" sh -c \
  'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" exec mysqldump -uroot --single-transaction --routines --events --triggers --no-tablespaces --databases mtrip_system mtrip_business' \
  > "$legacy_site_backup"
test -s "$legacy_site_backup"
printf 'Backup: %s\n' "$legacy_site_backup"
cp backend/services/merchant-service/app/Service/OnboardingFinalApprovalService.php \
  "${legacy_site_backup%.sql}-OnboardingFinalApprovalService.php"
git apply /tmp/mtrip-legacy-onboarding-approval.patch
# 强制目标使用当前服务器已同步的代码，不自动拉取；prod会重建镜像并校验迁移。
bash scripts/auto-deploy.sh merchant-service merchant-service-app --prod
bash deploy/mtrip.sh health --prod
BASH
```

备份或发布失败时停止后续操作，保留日志；服务可能仍停止。不要单独修改申请表站点或清空KYC。
补丁会留下该PHP文件的工作区修改。后续切换到包含本修复的正式提交时，应先核对并仅撤回此补丁
（先 `git apply -R --check /tmp/mtrip-legacy-onboarding-approval.patch`，再
`git apply -R /tmp/mtrip-legacy-onboarding-approval.patch`），随后拉取并重建服务；不得覆盖其他工作区修改。

成功后刷新后台并重新打开旧线索，使用超级管理员再次执行最终批准。原KYC、签署和审核记录保留；
成功时详情显示正式商户及待激活主账号，时间线记录迁站与最终批准。后台、账号和全部首批物业
均应归属站点7。若出现专属模板、混站或唯一性冲突，按具体提示核对；不同目标条款需另行处理，
不能仅在原站点重新签署后反复审批。

可只读核对同一测试线索：

```bash
docker exec -i "${MYSQL_CONTAINER:-mtrip-mysql-1}" sh -c \
  'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" exec mysql -uroot --default-character-set=utf8mb4 mtrip_business' <<'SQL'
SELECT a.id,a.app_no,a.site_id,a.merchant_id,a.account_status,a.final_approved_at,
  m.site_id AS merchant_site
FROM merchant_application a LEFT JOIN merchant_info m ON m.id=a.merchant_id
WHERE a.app_no='APP-2026-C55754D9E6';
SELECT b.id,b.site_id,b.kyc_status,s.id AS property_id,s.site_id AS property_site
FROM merchant_application_business b JOIN merchant_application a ON a.id=b.application_id
LEFT JOIN merchant_store s ON s.source_business_id=b.id
WHERE a.app_no='APP-2026-C55754D9E6';
SELECT t.action,t.note,t.operator_name,t.created_at
FROM merchant_verify_timeline t JOIN merchant_application a ON a.id=t.application_id
WHERE a.app_no='APP-2026-C55754D9E6' AND t.action IN ('onboarding_site_migrated','final_approved')
ORDER BY t.id;
SQL
```

本轮本机仅使用隔离数据验证兼容处理；目标服发布及真实线索的最终批准需按上述流程执行后复核。
