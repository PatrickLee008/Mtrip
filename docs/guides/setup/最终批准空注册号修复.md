# 最终批准空注册号冲突修复与测试服补救

## 原因与修复范围

2026-11-19 测试服 `APP-2026-C55754D9E6`（测试公司）最终批准报 MySQL 1062：
`Duplicate entry '' for key 'merchant_info.uk_credit_code'`。

注册号原本允许不提供：后台录入不是必填；`MerchantAppOnboardingService` 保存时允许省略，提交时
也不要求注册号；商户 App 公司信息页目前只提交公司名，没有注册号输入项。最终批准却把缺失值
写成 `merchant_info.credit_code=''`，与该列的唯一索引冲突。

本机排查时该列同样为 `VARCHAR(50) NOT NULL`，同样有唯一索引；本机只有一家商户，且其注册号
为空，唯一的一份申请已批准。第一家空注册号商户可以成功，第二家才失败，并非测试服独有问题。
旧最终批准回归夹具总是填写不同的注册号，未覆盖这一场景。

本次保留注册号可空的既有规则，不增加 App 或后台必填项：

- 最终批准将空字符串和纯空格注册号写为 `NULL`。
- 新迁移 `V20261119070000__allow-missing-merchant-registration-number.sql` 将正式商户注册号列
  改为允许 `NULL`，并将存量空字符串／纯空格转为 `NULL`。
- `uk_credit_code` 保留，真实非空注册号仍唯一；非空注册号原值保留。
- 空库初始化快照同步更新。历史迁移不改写。

## 现有数据怎样处理

1. **已批准／已激活商户**：迁移只规范化缺失的注册号，不删除商户、账号、物业或 KYC，也不变更
   访问码、激活状态、凭证和业务关联；更新该列会按表定义自动更新商户的 `updated_at`。
2. **本次批准失败的申请**：保留原申请、审核结果和签署记录。失败发生在创建商户的事务内；
   隔离回归已验证商户／账号／物业／凭证记录均回滚。先在目标服核对申请状态，发布后由管理员
   刷新详情、重新执行最终批准，无需重新注册或重做 KYC。
3. **已存在非空注册号的商户**：不改其值，不通过清空真实注册号来绕过冲突。

## 测试服执行步骤

以下在服务器仓库根目录（本次截图为 `/www/wwwroot/MTrip`）通过 Bash 执行。
先将本次代码、迁移及快照同步到目标仓库；本轮本地修改尚未提交／推送，不能直接拉取旧版本后执行。
默认 MySQL 容器为 `mtrip-mysql-1`，不同名称时先设置 `MYSQL_CONTAINER`。

### 1. 只读预检

```bash
bash scripts/db-migrate.sh --dry-run
docker exec -i "${MYSQL_CONTAINER:-mtrip-mysql-1}" sh -c \
  'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" exec mysql -uroot --default-character-set=utf8mb4 mtrip_business' <<'SQL'
SELECT COUNT(*) AS merchants,
  SUM(TRIM(credit_code) = '') AS blank_registration_numbers,
  SUM(credit_code IS NULL) AS missing_registration_numbers
FROM merchant_info;
SELECT id, app_no, reg_number, registration_status, merchant_kyc_status,
  merchant_id, account_status, final_approved_at, final_approval_request_id
FROM merchant_application WHERE app_no = 'APP-2026-C55754D9E6';
SQL
```

预期失败申请 `merchant_id=0`、`account_status=0`、
`final_approved_at=NULL`、`final_approval_request_id=NULL` 或空字符串。若已存在正式商户映射，
先检查实际状态，不手动重置这些字段。

预览应包含新版本 `20261119070000`。迁移工具会处理全部待执行版本；若还有倒序遗漏或失败账本，
先按[迁移指南](../../../database/migrations/README.md)处理，不跳过校验、不改历史 SQL 或手工伪造账本。

### 2. 暂停商户服务、备份并发布

安排短暂维护窗口并暂停其他自动部署；下面会暂时停止商户主池和 App 池，避免旧代码在迁移与
新镜像启动之间继续写入空字符串。`--prod` 使用无源码挂载的服务器栈，会重建镜像，不能只 restart。

```bash
bash <<'BASH'
set -euo pipefail
bash deploy/mtrip.sh stop merchant-service merchant-service-app --prod
mkdir -p deploy/backups
registration_backup="deploy/backups/before-registration-number-repair-$(date -u +%Y%m%d-%H%M%S).sql"
docker exec "${MYSQL_CONTAINER:-mtrip-mysql-1}" sh -c \
  'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" exec mysqldump -uroot --single-transaction --routines --events --triggers --no-tablespaces --databases mtrip_system mtrip_business' \
  > "$registration_backup"
test -s "$registration_backup"
printf 'Backup: %s\n' "$registration_backup"

# 强制目标不会 fetch/merge，使用已同步到本目录的修复代码。
# 数据库迁移先执行，再重建商户两个服务池；无需构建前端或重新发布 App。
bash scripts/auto-deploy.sh database merchant-service merchant-service-app --prod
bash scripts/db-migrate.sh --status
BASH
```

若备份、迁移或构建失败，停止后续步骤，保留日志和备份；服务可能仍处于停止状态。
不要为了回退将注册号列重新改为 NOT NULL：迁移后可合法存在多个 NULL，应先修复发布失败原因。

### 3. 数据与服务复核

```bash
docker exec -i "${MYSQL_CONTAINER:-mtrip-mysql-1}" sh -c \
  'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" exec mysql -uroot --default-character-set=utf8mb4' <<'SQL'
SELECT IS_NULLABLE FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = 'mtrip_business' AND TABLE_NAME = 'merchant_info' AND COLUMN_NAME = 'credit_code';
SELECT INDEX_NAME, NON_UNIQUE FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA = 'mtrip_business' AND TABLE_NAME = 'merchant_info' AND INDEX_NAME = 'uk_credit_code';
SELECT COUNT(*) AS remaining_empty_registration_numbers
FROM mtrip_business.merchant_info WHERE TRIM(credit_code) = '';
SQL
bash deploy/mtrip.sh health --prod
```

预期依次为 `YES`、`uk_credit_code / NON_UNIQUE=0`、空字符串数量 `0`，迁移账本无待执行版本，
商户两个服务池健康。随后登录测试后台，刷新并重新打开 `APP-2026-C55754D9E6`，确认门禁仍满足，
重新点击最终批准。成功后应显示待激活，且只有一个正式商户、一个主账号和一组首批物业映射。
在此之前不要手动改申请为“已批准”，也不需要给测试公司编造注册号。
