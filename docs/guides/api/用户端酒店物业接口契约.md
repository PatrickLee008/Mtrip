# 用户端酒店物业接口契约

> 版本：v1.1（阶段 6 已实现，2026-09-15）
> 本轮不修改 `client-app/**`。本文记录后端现状、目标行为和后续 App 对接方式。

## 1. 标识与统一响应

- 酒店使用 `propertyId`，房型使用 `roomTypeId`。
- 酒店接口不得要求或返回酒店 `goodsId/skuId` 作为主标识；兼容展示字段只允许在过渡期保留，客户端不得建立新依赖。
- 统一响应为 `{code,message,data}`；分页为 `data={list,total,page,pageSize}`。
- 站点从签名请求上下文取得，客户端不得通过请求体切换站点。

## 2. 接口清单

| 方法与路径 | 鉴权 | 主要入参 | 主要返回 | 当前状态 |

## 3. 普通搜索与排名

普通酒店搜索的候选集是全部满足发布门禁的物业，排名只叠加展示策略：

```text
全部本站点酒店物业
  -> 发布门禁过滤
  -> 搜索条件过滤
  -> 叠加已发布排名配置（可选）
  -> 默认/价格/评分/销量/距离排序
  -> 分页
```

- 没有排名记录的合格酒店仍出现在普通搜索结果中。
- 无排名酒店固定返回 `ranking_id=0,rank=0,pinned=0,featured=0`；未指定地区时仍返回物业自身的 `country_code/city_key`。
- `pinned/featured/rank` 只影响默认排序和推荐展示。
- 推荐榜单可以要求存在排名配置，但必须使用独立的榜单语义，不能改变普通搜索资格。
- `MarketplaceReader::searchable()` 实现普通搜索语义；`MarketplaceReader::published()` 保持已发布推荐/排名榜单语义。

## 4. 发布门禁

物业同时满足以下条件才可出现在用户端：

1. 正式商户已启用。
2. 物业状态有效，业务类型为 `hotel`。
3. 物业 KYC 已批准。
4. 物业内容审核通过且 `content_approved_version>0`。
5. 物业发布状态为已发布。
6. 物业经营状态为营业。
7. 至少存在一个 `status=1,publish_status=2,approved_version>0` 的房型。
8. 商户不在有效黑名单中。
9. 平台展示开关开启。

任一门禁失效后，普通搜索、详情、日历和评价列表应实时不可访问；历史订单仍保留并按订单快照履约和审计。

首次物业资料审批通过时，系统把 `display_enabled` 置为 `1`；后续资料版本审批不会重新打开管理员手工关闭的展示开关。物业首次发布同步置为 `status=1,operating_status=1`；下线只把 `publish_status` 置为下线，不清空经营状态。

## 5. 版本读取规则

- 物业详情读取最后一个批准版本，不读取当前编辑草稿或待审版本。
- 房型只读取 `approved_version>0` 且已发布、已启用的线上投影。
- 商户提交新版本后，旧线上版本继续展示，直到新版本批准并发布。
- 新版本被驳回时只更新审核状态与原因，不清空旧线上版本。

## 6. 后续 `client-app` 对接

后续独立 App 阶段只需执行以下适配，本轮不改代码：

1. 搜索结果、详情、日历、收藏、评价和预订统一传递 `propertyId/roomTypeId`。
2. 删除酒店流程对 `goodsId/skuId` 的兼容读取，门票流程继续使用这两个标识。
3. 对 `404/40901` 做酒店已下线或资格变化提示，不缓存绕过服务端门禁。
4. 以接口分页和排序结果为准，不在客户端重新拼接排名候选。
5. 使用隔离账号验证酒店发布、下线、内容新版本待审和房型停售后的实时表现。

## 7. 对接验收

- 合格但无排名记录的酒店可在普通搜索中出现。
- 推荐配置只改变推荐标记和默认排序，不决定普通搜索是否出现。
- 待审的新物业/房型版本不泄露到用户端，旧批准版本持续可见。
- KYC 撤销、商户暂停、物业停业、平台下线或最后一个房型停售后，酒店实时不可见。
- 两家同名酒店及同名房型始终通过 `propertyId/roomTypeId` 正确隔离。
