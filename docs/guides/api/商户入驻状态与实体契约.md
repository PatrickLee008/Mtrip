# 商户入驻状态与实体契约

> 版本：v1.0（阶段 0 冻结，2026-09-15）
> 依据：Merchant App PRD v1.0.3 模块 1、已确认的端到端业务流程、当前运行库与代码审计。
> 阶段 1 已实现数据库状态与归属模型，阶段 2 已实现注册草稿和基础注册审批，阶段 3 已实现双范围 KYC、电子签署、逐文件审核与重交；最终批准与激活能力仍按后续阶段交付。

## 1. 实体关系

| 概念 | 生命周期 | 系统实体 | 责任边界 |
|---|---|---|---|
| 商户 | 长期 | `merchant_info` | 法律主体、合同、结算、主账号、访问码和商户级 KYC 的归属主体 |
| 业务领域 | 配置/分类 | `business_type` | 酒店、租车、餐厅等能力分类；决定适用模板、访问码前缀和可见功能，不是独立登录主体 |
| 注册业务 | 仅入驻期 | `merchant_application_business` | 注册时重复填写的业务详情；酒店场景下一条注册业务对应一家首批物业 |
| 物业 | 长期 | `merchant_store.id`，对外称 `property_id` | 实际运营地点；承载物业 KYC、酒店资料、房型、库存、订单、评价、促销和员工授权 |

固定关系如下：

```text
merchant_application
  1 ── N merchant_application_business（申请期）
             │ 最终批准时一对一转换，source_business_id 保留来源
             ▼
merchant_info 1 ── N merchant_store/property（运行期）
```

- 基础注册批准只开放 KYC，不创建 `merchant_info`、`merchant_admin` 或物业。
- 最终批准要求商户级 KYC 与全部首批物业 KYC 均通过，并在同一事务中创建商户、主账号和全部首批物业。
- `merchant_application_business.id` 不得作为正式运营接口的物业 ID。
- 已认证商户新增物业时只执行物业专项 KYC，不重复商户级 KYC，也不重新生成商户访问码。

## 2. 目标状态机

三个主状态必须独立存储和返回，禁止再用单个 `merchant_application.stage` 同时表达注册、KYC 和账号状态。

### 2.1 `registrationStatus`

| 值 | 含义 | 可执行动作 |
|---|---|---|
| `draft` | OTP 已验证且草稿已创建 | 查询、自动保存、正式提交 |
| `submitted` | 已提交基础注册 | 查看状态 |
| `under_review` | 管理员正在审核基础资料 | 查看状态 |
| `resubmit_required` | 基础资料需补正 | 查看原因、修改、重新提交 |
| `approved` | 基础注册通过，KYC 已开放 | 进入 KYC |
| `rejected` | 基础注册终止 | 查看驳回原因 |

允许转换：

```text
draft -> submitted -> under_review -> approved
                         ├-> resubmit_required -> submitted
                         └-> rejected
```

### 2.2 `merchantKycStatus`

| 值 | 含义 | 可执行动作 |
|---|---|---|
| `locked` | 基础注册尚未通过 | 无 |
| `draft` | KYC 已开放，资料尚未提交 | 上传、替换、签署、提交 |
| `submitted` | 商户已提交 | 查看状态 |
| `under_review` | 管理员审核中 | 查看状态 |
| `resubmit_required` | 指定资料或签署信息需补正 | 查看原因、替换、重新提交 |
| `approved` | 商户主体 KYC 通过 | 等待首批物业全部通过或最终批准 |
| `rejected` | 商户主体 KYC 终止 | 查看原因 |

提交门禁：所有必需商户级文件齐全，并且已保存条款版本、签名、签署人身份和签署时间。

### 2.3 `accountStatus`

| 值 | 含义 | 工作台访问 |
|---|---|---|
| `not_created` | 尚未最终批准 | 禁止 |
| `pending_activation` | 最终批准完成，主账号和访问码已创建 | 只允许激活/认证接口 |
| `active` | 已完成至少一种登录方式关联和强制 OTP | 允许 |
| `suspended` | 平台暂停 | 禁止新会话，按平台规则处理已有业务 |
| `disabled` | 账号禁用或注销 | 禁止 |

最终批准与激活是两个事件：最终批准创建账号并进入 `pending_activation`；激活 OTP 成功后进入 `active`。

### 2.4 `propertyKycStatus`

| 值 | 含义 |
|---|---|
| `draft` | 物业专项资料草稿 |
| `submitted` | 已提交待审 |
| `under_review` | 管理员审核中 |
| `approved` | 物业 KYC 通过 |
| `rejected` | 物业 KYC 终止 |
| `resubmit_required` | 指定文件需补正 |

首批物业的申请期状态归属 `merchant_application_business`；最终批准后复制为对应 `merchant_store.kyc_status=approved`，并通过 `source_business_id` 保持一对一可审计关系。

### 2.5 酒店内容、房型和发布状态

| 维度 | 状态 | 规则 |
|---|---|---|
| 物业内容 | `draft/submitted/approved/rejected/withdrawn` | 待审或驳回版本不得覆盖已批准线上版本 |
| 房型版本 | `draft/submitted/approved/rejected/withdrawn` | 每个房型独立审核；待审版本不影响已发布版本 |
| 发布 | `unpublished/published/offline` | 只有发布门禁全部满足时才能进入 `published` |
| 经营 | `open/closed/platform_suspended/archived` | 独立于审核状态，实时影响消费者可见性 |

消费者普通酒店搜索资格由发布门禁决定。排名记录只提供推荐、置顶和排序信息，不得成为普通搜索的准入条件。

## 3. 文档归属

`merchant_verify_document` 后续只允许两种明确范围：

| `scopeType` | 主归属键 | 允许的辅助来源键 | 禁止 |
|---|---|---|---|
| `merchant` | `applicationId`（入驻期）或 `merchantId`（运行期） | 无 | 使用 `bizUnit` 表达同一份商户级资料 |
| `property` | 入驻期 `applicationBusinessId`；运行期 `propertyId` | `applicationId` 仅作审计来源 | 空物业归属、把申请业务 ID 当作 `propertyId` |

- `biz_unit` 仅作存量兼容读取，阶段 1 完成确定性迁移后停止新写入。
- 营业执照、法人/授权代表身份证明、银行账户与银行证明、税务登记、组织架构图属于商户级。
- 酒店经营许可证、经营场所产权/租赁协议及平台配置的酒店专项资料属于物业级。
- 模板由后端按 `scope_type + business_type + site_id` 返回，前端不得硬编码清单。

## 4. 访问码与登录身份

- 访问码恰好 6 位，大写字母数字，输入不区分大小写；酒店格式 `HXXXXX`，租车格式 `CXXXXX`。
- 访问码在同一商户类型内唯一，前缀必须与商户主业务类型一致；混合业态账号的主类型在最终批准前由管理员确认。
- 访问码只是登录标识之一，不能单独获得工作台访问权。
- 最终批准后必须向已验证手机号和/或邮箱发送激活通知与访问码，并记录逐渠道投递结果；应用内通知可以补充，不能代替可验证的外部交付。
- 商户主账号属于 `merchant_info`，物业账号和员工账号只获得授权范围，不拥有独立商户访问码。

## 5. 兼容映射

| 当前字段 | 当前含义 | 目标处理 |
|---|---|---|
| `merchant_application.stage` | 1-6 混合 CRM、KYC 和批准状态 | 保留只读兼容期，目标状态由三个独立状态字段驱动 |
| `merchant_application_business.kyc_status` | 0待办、1通过、2待核验、3审核中、4驳回 | 转换为首批物业 KYC 状态，补充明确的待重交状态 |
| `merchant_info.status` | 商户审核与启停混合 | 仅保留正式商户生命周期；入驻状态不再依赖它 |
| `merchant_info.access_status` | 0待设置、1可访问 | 映射 `pending_activation/active`，禁用状态仍由正式商户状态控制 |
| `merchant_store.kyc_status` | 0草稿、1通过、2待审、3审核中、4驳回、5待重交 | 语义保留，对外统一返回字符串枚举 |
| `merchant_store.content_status` | 0草稿、1待审、2通过、3驳回 | 增加版本级撤回语义；线上投影仍取最后批准版本 |
| `merchant_store.publish_status` | 0未发布、1已发布、2已下线 | 语义保留，对外统一返回字符串枚举 |

## 6. 全局不变量

1. 未通过基础注册，不允许访问 KYC 上传接口。
2. 未完成电子签署，不允许提交商户 KYC。
3. 商户级 KYC 或任一首批物业 KYC 未通过，不允许最终批准。
4. 最终批准事务失败时，不得留下半成品商户、账号、物业或访问码。
5. 同一 `applicationBusinessId` 最多映射一个 `propertyId`，且站点和商户必须一致。
6. 新增物业审批不得改变商户访问码、商户 KYC 或其他物业状态。
7. 酒店资料和房型的新待审版本不得改变消费者正在读取的已批准版本。
8. 消费者酒店查询只返回满足发布门禁的物业；有无排名配置不改变普通搜索资格。
9. 所有状态写入、OTP、签署、审批、凭证投递和账号恢复事件必须写审计日志。
10. 所有接口保持 `{code,message,data}`；分页保持 `data={list,total,page,pageSize}`；站点隔离始终由服务端执行。
