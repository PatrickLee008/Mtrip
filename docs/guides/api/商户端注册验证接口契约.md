# 商户端注册与验证接口契约（v1.0，由平台方主导定义）

> 依据：《mTrip_Merchant App PRD_v1.0_中文版.md》场景 1 / 模块 1 + 《mTrip_Super_Admin_Portal_PRD_Enterprise_v1.0_中文版.md》模块 11。
> 移动端（商户 App / Web）由其他团队开发，本文件为**平台方提供的接口契约**：字段、状态机与数据位以本文件为准。
> 前缀：`/api/v1/app/merchant/*`（网关 `app` 前缀，注册后由平台登记 `merchant → merchant_service` 映射）。
> 统一响应：`{code, message, data}`，成功 `code=0`；错误码见 `backend/shared/src/Constants/ErrorCode.php`。

---

## 1. 申请状态机（商户视角）

```
注册已提交 → 审核中 → 需要提交 KYC → KYC 已提交 → 验证中 → 已批准 / 已拒绝 / 需重新提交
   │                                                                   │
   └─(提交前可保存草稿)                                                 └─ 更正/替换文件后 → 验证中
```

状态与平台数据位映射：

| 商户端展示状态 | 平台依据 | 说明 |
|---|---|---|
| 草稿 | `merchant_application.stage=0`（预留） | 提交前保存 |
| 注册已提交 / 审核中 | `stage=1(新线索)` 或 `stage=2(已联系)` | 商户运营处理中 |
| 需要提交 KYC | `stage=3(已授予KYC访问权限)` | 已发送 KYC 要求 |
| KYC 已提交 | `stage=4(KYC进行中)` 且文档已上传 | 待转待验证 |
| 验证中 | `merchant_info.status=0`（待验证） | 授权管理员逐文件审核 |
| 需重新提交 | `merchant_info.status=6` | 附带受影响文件与原因 |
| 已批准 | `merchant_info.status=3` | 生成访问码；`access_status=0`（待设置2FA） |
| 已拒绝 | `merchant_info.status=2` | 附带拒绝原因与受影响文件 |
| 可访问仪表盘 | `status=3` 且 `access_status=1` | 完成 2FA 注册后置 1 |

## 2. 接口清单

### 2.1 注册与申请

| # | 接口 | 说明 |
|---|---|---|
| M1 | `POST /api/v1/app/merchant/register/otp-send` | 发送注册 OTP（手机或邮箱） |
| M2 | `POST /api/v1/app/merchant/register/otp-verify` | 校验 OTP，返回临时注册令牌 |
| M3 | `POST /api/v1/app/merchant/application/save` | 保存申请草稿或提交（`draft=0/1`），入参含公司级信息+业务列表 |
| M4 | `POST /api/v1/app/merchant/application/submit` | 正式提交申请（进入审核中） |

### 2.2 KYC

| # | 接口 | 说明 |
|---|---|---|
| M5 | `GET /api/v1/app/merchant/application/kyc-requirements` | 查询分配的 KYC 要求（按业务/业务类型） |
| M6 | `POST /api/v1/app/merchant/kyc/upload` | 上传单份文件（业务 ID + 文档类型 + 文件） |
| M7 | `POST /api/v1/app/merchant/kyc/submit` | 提交全部 KYC（触发 `confirmation_status=1`） |
| M8 | `GET /api/v1/app/merchant/application/status` | 查询申请状态 + 受影响文件 + 拒绝/重交原因 |

### 2.3 认证与 2FA

| # | 接口 | 说明 |
|---|---|---|
| M9 | `POST /api/v1/app/merchant/auth/access-code-verify` | 首次/回头登录：校验商户访问码（+OTP 上下文） |
| M10 | `POST /api/v1/app/merchant/auth/2fa/setup-info` | 获取 2FA 设置信息（二维码内容/手动密钥，仅 `two_fa_status in (0,2)` 且 access_status=0 时返回） |
| M11 | `POST /api/v1/app/merchant/auth/2fa/verify` | 提交 6 位验证码完成注册/登录；注册成功置 `two_fa_status=1, access_status=1` |
| M12 | `POST /api/v1/app/merchant/auth/logout` | 退出（含 Web 二维码登录会话） |

## 3. 关键字段与数据位（平台侧）

- `merchant_info.access_status`：0=待设置 2FA，1=已设置（PRD：完成访问安全设置才能访问仪表盘）。
- `merchant_info.two_fa_status`：0=未注册，1=活跃，2=需要重置（重置后商户下次登录重新注册）。
- `merchant_info.two_fa_secret_enc`：2FA 设置密钥（AES 加密存储）；仅注册流程（M10/M11）消费，**管理端永不展示**。
- `merchant_info.access_code`：唯一商户访问码（批准后生成；重新生成使旧码失效）。
- `merchant_application_business.*`：业务级联系方式（contact_name/contact_phone/contact_email）与 KYC 状态。
- `merchant_verify_document.resubmit_required_at`：受影响文件标记（需重交）。
- `merchant_application.rejected_doc_ids`：拒绝时受影响文件快照。

## 4. 对接说明

1. 移动端未开发期间，管理端冒烟以“模拟商户”方式完成（admin 创建申请 → 发送 KYC → 直接构造文档提交）。
2. M1-M8 由移动端实现 UI，平台提供契约字段与状态位；M9-M12 涉及安全认证，建议移动端与平台联合评审后再实现。
3. 通知（批准/访问码/重交/2FA 重置）当前为记录+契约，真实发送通道接入后由平台统一推送。
