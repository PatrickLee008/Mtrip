# 商户端注册、KYC、激活与登录接口契约

> 版本：v1.4（阶段 5 已实现激活、四种登录与账号恢复，2026-09-15）
> 依据：Merchant App PRD v1.0.3 模块 1 与已确认整改流程。
> 本轮不修改 `merchant-app/**`。本文包含目标接口和当前实现状态；标记“预留/待整改”的接口不能当作已上线能力。

## 1. 通用规则

- Merchant App 前缀：`/api/v1/app/merchant/*`；请求必须通过 App 客户端鉴权，并携带 `X-Site-Id`。本阶段只实现后端契约，不修改 `merchant-app/**`。
- Merchant Web 前缀：`/api/v1/merchant/*`；公开认证接口不依赖工作台 JWT。没有站点头时，邮箱、手机号或 Google 身份只在全平台唯一匹配到一个账号时才继续。
- 响应：`{code,message,data}`；分页：`data={list,total,page,pageSize}`。
- 注册阶段使用短期 `registrationToken`；最终批准后激活阶段使用一次性 `activationToken`；工作台使用商户 JWT。
- 所有 Token 绑定站点、用途、主体和过期时间，不接受请求体覆盖站点或身份。
- 手机号和邮箱在初始注册时同时必填；`otpChannel=email|sms` 只决定本次 OTP 投递渠道。
- 电话、邮箱、OTP、访问码和签名数据必须脱敏展示；原始敏感值按项目加密规范存储。
- 状态与实体语义以[商户入驻状态与实体契约](./商户入驻状态与实体契约.md)为准。

## 2. 注册与草稿

| 方法与路径 | 请求/返回要点 | 目标行为 | 当前状态 |
|---|---|---|---|
| `GET /register/config` | 返回可用 OTP 渠道、长度、有效期、冷却规则 | 前端只展示后端启用渠道 | 已实现基础版 |
| `POST /register/otp-send` | `phone,email,otpChannel` | 同时校验两种联系方式，向选定渠道发送 6 位 OTP | 已实现 |
| `POST /register/otp-verify` | `phone,email,otpChannel,otpCode` | 验证成功原子创建/恢复草稿，返回 `registrationToken,applicationId` | 已实现 |
| `GET /application/detail` | `registrationToken,applicationId` | 返回已保存公司、注册业务、步骤和完成度 | 已实现 |
| `POST /application/save` | 公司字段、`businesses[]`、`currentStep` | 增量保存；用 `applicationBusinessId/clientRef` 幂等更新，保存真实业务类型 | 已实现 |
| `POST /application/submit` | `applicationId` | 校验完整资料后进入基础注册审核；重复提交幂等 | 已实现 |
| `GET /application/status` | `applicationId` | 分别返回注册、商户 KYC、首批物业 KYC、当前条款和账号状态 | 已实现 |

`businesses[]` 的酒店最小字段：

```json
{
  "clientRef": "local-uuid",
  "businessName": "Example Hotel",
  "businessType": "hotel",
  "countryCode": "MM",
  "cityKey": "yangon",
  "address": "...",
  "contactName": "...",
  "contactPhone": "+95...",
  "contactEmail": "..."
}
```

保存成功后返回稳定 `applicationBusinessId`。`clientRef` 只用于首次保存幂等，不得成为正式物业 ID。

## 3. 基础注册审批后的 KYC

| 方法与路径 | 请求/返回要点 | 目标行为 | 当前状态 |
|---|---|---|---|
| `GET /application/kyc-requirements` | `applicationId` | 返回 `merchantKyc.documents[]`、`initialProperties[]`、当前条款签署状态和最终批准门禁 | 已实现 |
| `POST /kyc/upload` | multipart：`scopeType,applicationId,applicationBusinessId?,docType,file` | 商户级不传业务 ID；物业级必须传首批业务 ID；只允许草稿或被退回范围写入 | 已实现 |
| `GET /agreements/current` | `applicationId` | 返回当前条款 ID、版本、完整正文、正文摘要和签署状态 | 已实现 |
| `POST /agreements/read-confirm` | `applicationId,agreementId,version,scrollConfirmed=true` | 完整滚动后换取 30 分钟有效、绑定申请和条款摘要的 `readReceipt` | 已实现 |
| `POST /agreements/sign` | `applicationId,agreementId,version,readReceipt,signerName,signerRole,signature` | `signature` 为不超过 1MB 的 PNG/JPEG Base64；保存文件摘要、签署人、时间、IP 和 User-Agent | 已实现 |
| `POST /kyc/submit` | `applicationId` | 当前条款已签署且所有可编辑范围的必需文件齐全后提交；已通过范围保持不变 | 已实现 |
| `GET /application/status` | `applicationId` | 返回各范围审核结果、驳回原因、需重交文件、当前条款及 `finalApproval.ready/reasons` | 已实现 |

## 4. 最终批准与激活

最终批准由管理端触发。商户端只能查询结果、接收通知和完成激活。

| 方法与路径 | 请求/返回要点 | 状态 |
|---|---|---|
| `GET /auth/config` | 返回登录方式、Google 可用性、OTP 有效期/冷却/次数及 `biometricAvailableOnWeb=false` | 已实现 |
| `POST /activation/start` | `accessCode`，或 `username,temporaryPassword`；返回 `activationToken,expiresIn,profile` | 已实现 |
| `GET /activation/profile` | `activationToken`；返回脱敏手机号、邮箱及已关联方式 | 已实现 |
| `POST /activation/otp-send` | `activationToken,channel=email|sms`；返回 OTP challenge 和脱敏收件人 | 已实现 |
| `POST /activation/otp-verify` | `challengeToken,otpCode`；返回新的 `activationToken` 供后续步骤使用 | 已实现 |
| `POST /activation/totp/setup` | `activationToken`；返回 `manualKey,otpauthUri` | 已实现 |
| `POST /activation/totp/verify` | `activationToken,twoFaCode`；关联 Google Authenticator | 已实现 |
| `POST /activation/google-link` | `activationToken,googleIdToken`；校验标准 Google ID Token 后关联 | 已实现，真实提供商配置待补 |
| `POST /activation/finish` | `activationToken`；原子激活商户、主账号和申请账号状态并签发 JWT | 已实现 |

激活 OTP 成功后，客户端必须使用响应中的新 `activationToken`，旧身份确认 Token 不再用于绑定或完成激活。Authenticator 与 Google 关联均为可选；未关联 Authenticator 时访问码登录不可用。激活完成前不签发工作台权限 JWT。完成时一次性初始密码失效，`merchant_admin.status:2→1`、`merchant_info.status:1→3`、`merchant_application.account_status:1→2` 在同一事务内生效。

## 5. 再次登录

| 登录方式 | 目标接口 | 必需验证 | 当前状态 |
|---|---|---|---|
| 访问码 | `POST /auth/challenge`，`method=access_code,identifier=HXXXXX/CXXXXX` | Google Authenticator OTP | 已实现 |
| Google | `POST /auth/challenge`，`method=google,googleIdToken` | 已关联 Google 身份 + 已验证联系渠道的 mTrip OTP | 已实现，真实提供商配置待补 |
| 邮箱 | `POST /auth/challenge`，`method=email,identifier` | 注册且已验证邮箱 + 邮箱 OTP | 已实现 |
| 手机 | `POST /auth/challenge`，`method=sms,identifier` | 注册且已验证手机号 + 短信 OTP | 已实现 |
| 完成挑战 | `POST /auth/challenge/verify`，`method,challengeToken,otpCode` | 按 challenge 指定的 OTP | 已实现 |
| 退出 | `POST /auth/logout` | 有效商户 JWT | 已有基础版 |

- 选择 Google、邮箱或手机登录时不要求访问码。
- 访问码不能单独登录；所有方式都必须执行对应 OTP。
- OTP 请求、失败、锁定、登录方式变更、设备信任与恢复事件都写审计日志。
- Web 门户不提供生物识别。

未知邮箱或手机号返回与已存在账号相同结构的伪 challenge，只有验证码校验阶段失败，避免账号枚举。OTP 有效期 5 分钟、重发冷却 60 秒、最多错误 5 次；challenge 使用后立即失效，不能重放。旧用户名/密码 + Authenticator 接口继续保留给历史账号，但不作为新入驻主流程。

## 6. 账号恢复

| 方法与路径 | 请求/返回要点 | 状态 |
|---|---|---|
| `POST /auth/recovery/challenge` | `method=email|sms,identifier`；只接受激活时已验证的注册联系方式 | 已实现 |
| `POST /auth/recovery/verify` | `challengeToken,otpCode`；返回短期 `recoveryToken` | 已实现 |
| `POST /auth/recovery/totp/setup` | `recoveryToken`；生成新的 Authenticator 设置密钥 | 已实现 |
| `POST /auth/recovery/totp/verify` | `recoveryToken,twoFaCode`；保存新密钥并签发 JWT | 已实现 |

恢复完成会递增 `merchant_admin.auth_version`，撤销旧 JWT、旧 Authenticator 和其他未完成 challenge。审计只记录恢复请求、成功、失败和登录事件，不记录验证码或 Authenticator 密钥。

## 7. 商户移动 App 生物识别预留

以下接口仅冻结契约方向，留到独立的 `merchant-app` 阶段实现。当前路由不存在，客户端不得提前调用：

| 方法与路径 | 预留请求/返回 | 用途 |
|---|---|---|
| `POST /trusted-devices/register` | JWT；`deviceId,deviceName,platform,publicKeyJwk,credentialId` → `trustedDeviceId,deviceCredential,expiresAt` | 完整 OTP 登录后登记设备公钥和设备凭据 |
| `POST /trusted-devices/biometric-enable` | JWT；`trustedDeviceId,deviceSignature` → `enabledAt` | 用户通过系统生物识别后主动开启本机快捷登录 |
| `POST /auth/biometric/challenge` | 客户端鉴权 + `X-Site-Id`；`deviceId,credentialId` → `challengeId,nonce,expiresIn` | 获取一次性设备签名挑战 |
| `POST /auth/biometric/verify` | `challengeId,signature` → 标准 `LoginResult` | 校验设备私钥签名并签发工作台会话 |
| `DELETE /trusted-devices/current` | JWT；`trustedDeviceId` → `null` | 关闭或使当前设备凭据失效 |

设备私钥和生物特征只保存在操作系统安全区，服务端只保存公钥、凭据摘要、账号/站点绑定、状态、过期时间和审计。服务端不接收、存储或比对人脸/指纹。App 本地连续三次生物识别失败、操作系统锁定、设备变化、设备凭据过期/撤销或服务端签名校验失败时，必须清除本地快捷登录状态并回退到完整登录方式；完整 OTP 登录后才能重新登记。

## 8. 访问码与通知

- 酒店访问码为 `H` 加 5 位大写字母数字；租车为 `C` 加 5 位大写字母数字。
- 唯一性按大小写不敏感校验；服务端将输入规范化为大写。
- 最终批准后通过已验证邮件和/或短信发送访问码及激活入口，并记录 `queued/sent/delivered/failed`。
- 重发不默认重新生成访问码；重新生成必须是独立高权限操作，并使旧码失效。
- 日志、接口错误和通知审计不输出 OTP、Authenticator 密钥或完整访问码。
