# 下一步执行计划

## 总目标

把 Mtrip Ops 从“可查看的运维控制台”推进到“发布与服务状态闭环”的运维系统。核心是解决三个问题:

1. 服务真实状态是否准确。
2. 当前运行的版本是否可追踪。
3. 发布动作是否可预检、可执行、可审计、可验证。

## 阶段 1:Docker 状态读取修正

### 背景

当前服务页能展示 Docker 相关字段,但如果运行 Mtrip Ops 的用户没有 Docker API 权限,页面会显示 `unknown`。用户在服务器 root 下执行 `docker ps` 可以看到主池、MySQL、Redis 都在运行,说明容器本身没问题,问题在 Ops 进程权限或 Docker 命令配置。

### 目标

- 让 Ops 能稳定读取 `docker ps -a`、`docker stats --no-stream`、`docker inspect`。
- 服务页准确显示 running/stopped/exited/missing/unknown。
- 显示启动时间、运行时长、镜像、CPU、内存、网络、Block IO、PIDs。
- Docker 不可读时给出明确修复建议。

### 任务

- [x] 确认 Ops 当前运行用户:本机验证为 `ctyun`(uid/gid `1000/1000`),生产需按实际 systemd 用户复核。
- [x] 开发环境选择一种 Docker 读取方式:
  - 运行用户加入 docker 组。
  - 当前采用 `ops.config.json` / 默认配置 `dockerCommand: ["sudo", "-n", "docker"]`,需要运行用户配置 NOPASSWD。
- [ ] 生产环境设计受限 Docker 读取方式:
  - 优先 docker-socket-proxy。
  - 或独立 runner 执行白名单 Docker 命令。
- [x] 服务页增加 Docker 权限诊断卡片。
- [x] 增加 `/api/diagnostics/docker` 诊断接口。
- [x] 增加 Docker 命令超时、错误码、stderr 展示。

### 验收

- `/services` 主池服务显示 `running`。
- MySQL/Redis 显示 `running`。
- 如果 APP 孪生池未启动,显示 `missing`,并提示 `/api/v1/app/*` 可能 502。
- 如果 Docker 不可读,显示 `unknown`,并展示权限修复建议。

## 阶段 2:发布版本信息 release.json

### 背景

Docker 默认能提供启动时间和镜像信息,但不能自动提供“业务版本号、发布时间、发布说明”。这些是发布系统语义,需要 Mtrip 的部署脚本写入。

### 目标

- 增加 `deploy/release.json` 作为第一阶段发布元数据来源。
- 服务页展示版本号、发布时间、Git SHA、发布说明。
- 发布页展示上次发布记录。
- 后续 `auto-deploy.sh` 成功后自动写入 release.json。

### 推荐格式

```json
{
  "global": {
    "version": "2026.09.02-001",
    "publishedAt": "2026-09-02T18:30:00+08:00",
    "gitSha": "abcdef1234567890",
    "notes": "订单与 APP 孪生池发布"
  },
  "services": {
    "user-service": {
      "version": "2026.09.02-user-001",
      "publishedAt": "2026-09-02T18:31:00+08:00",
      "gitSha": "abcdef1234567890",
      "notes": "用户登录与常旅客修复"
    }
  }
}
```

### 任务

- [ ] 增加 release.json 读取状态展示。
- [ ] 增加 release.json 缺失提示。
- [ ] 增加发布页“填写发布说明”表单。
- [ ] 发布成功后写入 global 与 services 节点。
- [ ] 增加 release 历史记录,避免只保留最后一次。
- [ ] 后续可选:compose/Dockerfile 增加 OCI labels。

### 验收

- 未配置 release.json 时显示“未配置”,且给出配置链接。
- 配置 release.json 后,服务页能显示版本、发布时间、Git SHA、发布说明。
- 单服务发布后只更新对应 service 元数据。

## 阶段 3:完整 Git 发布流程

### 目标

把发布页流程固定为:

1. Git status
2. Git fetch
3. Git pull --ff-only
4. auto-deploy dry-run
5. DB backup
6. auto-deploy 执行
7. mtrip health
8. 写 release.json
9. 写审计日志

### 任务

- [ ] 发布页增加流程状态机。
- [ ] 每一步显示 running/success/fail/skipped。
- [ ] 支持只执行到 dry-run。
- [ ] 支持正式部署二次确认。
- [ ] 正式部署前检查工作区 dirty 状态。
- [ ] 正式部署后自动 health。
- [ ] 失败时展示处理建议。
- [ ] 记录完整 stdout/stderr。

### 验收

- 工作区 dirty 时阻止正式部署。
- Git 分叉或非 ff-only 时阻止部署。
- dry-run 能展示部署决策。
- 部署后 health 失败时发布记录标记失败。

## 阶段 4:单服务发布流程

### 目标

支持单个服务的运维发布和故障处理,但不能绕过风险检查。

### 任务

- [ ] 选择服务后展示相关健康、日志、负载、版本。
- [ ] 支持单服务 logs/restart/build。
- [ ] 操作前提示影响范围。
- [ ] 如果选择主池共享服务,提示是否需要同步 APP 孪生池。
- [ ] 如果选择 APP 服务,提示只影响 `/api/v1/app/*`。
- [ ] 操作后自动检查 health。
- [ ] 操作后自动抓取最近错误日志。
- [ ] 写入单服务 release 元数据。

### 验收

- 单服务 restart 后,页面展示新的启动时间和运行时长。
- 单服务 build 后,页面展示新镜像或新版本信息。
- APP 孪生池未启动时,操作页明确提示不可同步或需要先启动 APP 池。

### 目标

### 任务

- [ ] 服务状态自动刷新。
- [ ] QPS 趋势图。
- [ ] 5xx 趋势图。

- [ ] CPU/内存趋势图。
- [ ] 支持刷新频率 30s / 1m / 5m。

### 验收

- 图表能展示最近 15 分钟趋势。
- 大屏模式隐藏操作按钮,只保留监控数据。

## 阶段 6:业务监控与在线用户

### 目标

把运维监控从系统层扩展到业务层。

### 任务

- [ ] 创建业务库只读账号。
- [ ] 订单数、GMV、支付成功率、核销率。
- [ ] 商户入驻、待审核、驳回、已验证统计。
- [ ] 商品上架、房型审核、库存异常统计。
- [ ] 站点维度筛选。
- [ ] 先按最近请求估算在线用户。
- [ ] 后续改业务中间件写 Redis TTL,得到真实在线用户。

### 验收

- 业务看板能按站点查看。
- 在线用户能区分游客/登录用户/商户后台/管理后台。
- 只读账号不能执行写操作。

## 优先级建议

下一次开发建议先做:

1. Docker 状态读取诊断与修正。
2. release.json 展示与写入。
3. 发布页正式流程状态机。

这三项完成后,Ops 才能准确回答“现在跑的是什么、什么时候发布的、发布是否成功”。
