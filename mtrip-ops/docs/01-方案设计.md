# Mtrip Ops 方案设计

## 目标

建设一套独立于 Mtrip 业务项目的轻量运维服务软件,用于监控和管理平台运行情况:

- 系统状态:主机、磁盘、容器、网关、MySQL、Redis。
- 服务状态:8 个主池服务 + 5 个 APP 孪生池服务。
- 服务负载:CPU、内存、重启次数、healthz 延迟、慢请求。
- 业务日志:请求日志、异常日志、按服务/状态码/关键词检索。
- 流量情况:QPS、状态码分布、Top API、5xx/429/502、P95。
- 用户在线:先按最近请求估算,后续用 Redis TTL 做真实在线。
- 发布管理:发布预检、自动部署、服务重启、健康检查、DB 备份、DB apply。

## 取舍

不直接上 Prometheus/Grafana/Zabbix 全家桶,原因是当前最急的是“Mtrip 专属运维面板 + 发布管理闭环”。专业监控栈后续可以作为数据源接入,但第一版不承担其部署复杂度。

第一版采用:

- Node.js 单体服务。
- 服务端渲染 HTML,不做前后端分离。
- 零依赖 MVP,后续按需引入 Fastify、SQLite、Nunjucks、ECharts。
- 默认只读,动作显式开启。
- 所有危险动作由白名单 runner 执行,保留审计。

## 当前 Mtrip 部署适配

Mtrip 当前有三个关键运维入口:

- `deploy/mtrip.sh`:统一启停、构建、状态、日志、健康检查。
- `scripts/auto-deploy.sh`:ff-only 自动部署与精准重启。
- `scripts/db-backup.sh` / `scripts/db-apply.sh`:备份与增量 SQL。

Mtrip Ops 不重新发明部署流程,而是包装这些入口:

- 发布前先 dry-run,展示“前端构建/主池重启/APP 孪生重启/镜像重建/DB 变更”。
- 发布前自动跑 DB 备份。
- 发布后自动跑 `mtrip.sh health`。
- 失败时保留命令输出和审计,提示人工处理。

## 数据采集

| 数据 | 第一版来源 | 后续增强 |
|---|---|---|
| 服务健康 | `http://127.0.0.1:<port>/healthz` | 容器内探 APP 孪生池 |
| 容器状态 | `deploy/mtrip.sh status` | Docker Engine API / dockerode |
| 请求日志 | `deploy/logs/*/request-*.log` | SQLite FTS5 + 实时 tail |
| 异常日志 | `deploy/logs/*/hyperf-*.log` | 告警规则 |
| 网关流量 | OpenResty access log | 挂载 gateway logs 到宿主 |
| 在线用户 | 最近请求 IP/UA/token 粗估 | Redis 在线 TTL |
| 业务指标 | 暂不直连数据库 | 只读 MySQL 账号查询 |

## 页面

1. 总览:健康、异常、流量、容器状态。
2. 服务:主池/APP 池/基础设施服务状态与操作入口。
3. 日志:服务维度日志列表、tail、搜索。
4. 流量:状态码、慢请求、Top API、错误接口。
5. 在线:活跃 IP、用户、站点、设备。
6. 发布:dry-run、备份、部署、health、审计。
7. 告警:规则、事件、通知渠道。
