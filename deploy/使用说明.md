# mtrip.sh 使用说明(服务启停脚本)

> 位置:`deploy/mtrip.sh` | 适用:Linux / macOS / Windows(Git Bash、WSL)
> 本脚本是 `deploy/README.md` 各场景 docker compose 命令的封装入口,两者语义一致。
> Windows PowerShell 原生环境请直接用 `deploy/README.md` 里的命令。

## 0. 一分钟上手

```bash
cd deploy
chmod +x mtrip.sh          # 首次需要(从 Windows 拷过来的仓库尤其注意)
./mtrip.sh build           # 首次:构建镜像 + 启动全部服务(分钟级)
./mtrip.sh health          # 验证:8 个微服务 + 网关探活
```

之后日常只需:

```bash
./mtrip.sh start           # 启动
./mtrip.sh restart goods-service   # 改完 PHP 代码热重启(约 2 秒)
./mtrip.sh stop            # 停止
```

脚本可从任意目录调用(内部自动 `cd` 到 `deploy/`),例如 `./deploy/mtrip.sh status`。

## 1. 命令一览

| 命令 | 等价 docker compose | 说明 |
| --- | --- | --- |
| `start [服务名...]` | `up -d` | 启动,不重建镜像;缺 `.env` 时自动从 `.env.example` 生成 |
| `build [服务名...]` | `up -d --build` | 重建镜像并启动;改 Dockerfile / 新增 composer 依赖时用 |
| `restart [服务名...]` | `restart` | 热重启;只改 PHP 代码时用,约 2 秒/个 |
| `stop [服务名...]` | `stop` | 停止容器,保留容器与数据 |
| `down` | `down` | 删除容器与网络,**保留数据卷**(数据不丢) |
| `clean` | `down -v` | 删除容器与数据卷(**数据库清空**,需输入 `yes` 确认) |
| `status` / `ps` | `ps` | 容器状态 |
| `logs [服务名...]` | `logs -f --tail=100` | 跟踪日志,Ctrl+C 退出 |
| `health` | — | 8 个微服务 `/healthz` + 网关链路探活 |
| `help` | — | 帮助 |

选项:

| 选项 | 作用 |
| --- | --- |
| `--prod` | 只用 `docker-compose.yml`,跳过 `docker-compose.override.yml` 的开发热挂载(生产部署用) |

环境变量:

| 变量 | 作用 |
| --- | --- |
| `MTRIP_YES=1` | `clean` 跳过交互确认(CI / 脚本化重建用,慎用) |

可用服务名:

```
system-service  user-service  goods-service     order-service
merchant-service finance-service marketing-service payment-service
mysql  redis  gateway
```

不传服务名 = 作用于全部服务;传了未知服务名脚本直接报错退出(防拼写错误静默失败)。

## 2. 按场景选命令(勿一律 build)

| 场景 | 命令 | 耗时 |
| --- | --- | --- |
| 只改 PHP 代码(`app/`、`config/`、`backend/shared/src`) | `./mtrip.sh restart goods-service` | ~2 秒 |
| 改了 `docker-compose.yml` / `.env` 环境变量 | `./mtrip.sh start` | ~10 秒 |
| 新增 composer 依赖 / 改 Dockerfile | `./mtrip.sh build user-service` | 分钟级 |
| 改了 `database/` 初始化 SQL(需重跑建表) | `./mtrip.sh clean; ./mtrip.sh build` | 分钟级 |
| 改了网关路由 `openresty/conf.d/mtrip.conf` | `./mtrip.sh restart gateway` | ~2 秒 |

热重启原理:`docker-compose.override.yml` 把本地 `app/`、`config/`、`backend/shared/src` 挂进容器覆盖镜像内代码,
`restart` 后 Hyperf 重新扫描即生效,不需要重建镜像。加 `--prod` 时不挂载,改代码必须 `build`。

## 3. 脚本替你处理的两件事

1. **自动生成 `.env`** —— `start` / `build` 发现 `deploy/.env` 不存在时,自动 `cp .env.example .env` 并告警。
   生产环境务必手动修改其中的 `MYSQL_*` 密码与 `MTRIP_JWT_SECRET` / `MTRIP_AES_KEY` / `MTRIP_ADMIN_AES_KEY`。
2. **自动重启网关** —— `start` / `build` 会重建业务容器,容器 IP 变化后 OpenResty 仍缓存旧上游 IP,
   表现为「服务 healthz 正常但网关全部 502」。脚本在 `up` 之后自动 `restart gateway` 规避。
   (`restart xxx-service` 不换 IP,不触发此问题,脚本也就不会多此一举重启网关。)

## 4. 启动后的入口

| 入口 | 地址 | 备注 |
| --- | --- | --- |
| 网关(admin/app/merchant/supplier 接口统一入口) | http://localhost:8081 | 端口取 `.env` 的 `GATEWAY_HOST_PORT` |
| 微服务直连 healthz | 9501~9508 | system/user/goods/order/merchant/finance/marketing/payment |
| MySQL | localhost:3307 | `MYSQL_HOST_PORT`,账号见 `.env` |
| Redis | localhost:6380 | `REDIS_HOST_PORT` |

`start` / `build` 成功后脚本会打印上述入口(端口值实时从 `.env` 读取)。

## 5. health 命令读法

```bash
./mtrip.sh health
```

- 8 个微服务逐个 `GET /healthz`,期望 **200**。
- 网关 `GET /healthz` 期望 **200**。
- 网关转发 `POST /api/v1/app/auth/login`(不带签名头)期望 **401** —— 说明转发链路与签名中间件都正常。
  返回 **502** 表示上游不可达,执行 `./mtrip.sh restart gateway`。
- 全通过退出码 0,有失败项退出码 1(可直接用于 CI / 部署后门禁)。

刚 `build` 完容器需要 10~30 秒预热,首次探活失败先等一会儿重试;持续失败用 `./mtrip.sh logs <服务名>` 看日志。

## 6. 日志

- 文件日志挂载在 `deploy/logs/<服务名>/`:`hyperf.log`(异常,按天滚动)、
  `request.log`(全量请求,需 `.env` 设 `MTRIP_REQUEST_LOG=true`)。
- 容器实时输出:`./mtrip.sh logs order-service`。

## 7. 国内网络:两处必须换源

`build` 会拉两类东西,两类都可能被墙,**换源位置不同,别混**:

### 7.1 Docker 镜像(mysql / redis / openresty / hyperf 基础镜像)

配置文件位置取决于 Docker 的安装方式,**snap 版不读 `/etc/docker/daemon.json`**:

| 安装方式 | 配置文件 | 重启命令 |
| --- | --- | --- |
| apt / deb | `/etc/docker/daemon.json` | `systemctl restart docker` |
| **snap** | `/var/snap/docker/current/config/daemon.json` | `snap restart docker` |

用 `ps -ef | grep dockerd` 看 `--config-file=` 参数即可确认当前用哪个。可用源(截至 2026-08 实测):
`https://docker.m.daocloud.io`、`https://docker.1ms.run`、`https://docker.xuanyuan.me`。
**已失效**:`docker.mirrors.ustc.edu.cn`(DNS 都不解析)、`hub-mirror.c.163.com`。

改完必须重启 daemon,再用 `docker info | grep -A4 "Registry Mirrors"` 确认生效。

### 7.2 composer 依赖包(8 个 PHP 服务构建时)

由 `deploy/.env` 的 `COMPOSER_MIRROR` 控制,默认已设为阿里云:

```ini
COMPOSER_MIRROR=https://mirrors.aliyun.com/composer/
```

它经 `docker-compose.yml` 的 `build.args` 传给各服务 Dockerfile 的 `ARG COMPOSER_MIRROR`,非空时执行
`composer config -g repos.packagist composer "$COMPOSER_MIRROR"`。**留空 = 官方 packagist**,海外/生产构建行为不变。

为什么必须换:官方 packagist 的元数据能通,但 **dist 包下载走 `api.github.com`**,容器内基本必超时——
报错长这样,而且 8 个服务并行卡 4 分钟:

```
Failed to download doctrine/deprecations from dist: curl error 28 while downloading
https://api.github.com/repos/... Connection timed out after 10006 milliseconds
```

挂 HTTP 代理通常解决不了这个:多数本地代理(clash/mihomo 等)只监听 `127.0.0.1`,容器根本够不着;
即使用 `network: host` 够到了,代理节点也未必能过 GitHub 的 zipball 下载。阿里云镜像直接接管 dist,**不碰 GitHub**。

### 7.3 云主机必查:docker0 与出口网卡的 MTU 不一致

换源换对了仍然 `curl error 28 ... Connection timed out`,先比一眼 MTU:

```bash
cat /sys/class/net/docker0/mtu          # Docker 网桥,默认 1500
ip route show default                    # 找出出口网卡名,如 ens10
cat /sys/class/net/ens10/mtu            # 云主机常见 1450(VXLAN/隧道封装余量)
```

**出口网卡 < 1500 就必须改 Docker 的 MTU。** 否则容器按 1500 发包,超出部分要靠 ICMP
"fragmentation needed" 做路径 MTU 发现,而云厂商的安全组普遍丢弃这类 ICMP,形成**MTU 黑洞**:

- 小包正常 → composer 元数据能拉到,进度条能动;
- 大包(TLS 证书、`packages.json`、dist 压缩包)全部卡满超时 → `curl error 28`;
- 宿主机 `curl` 同一地址却秒开(宿主机走的就是 1450),极易误判成"源不可用"而反复换源。

改法(以 snap 版为例,deb 版改 `/etc/docker/daemon.json` 并 `systemctl restart docker`):

```jsonc
{
  "log-level": "error",
  "registry-mirrors": ["https://docker.m.daocloud.io"],
  "mtu": 1450          // 与出口网卡一致
}
```

```bash
snap restart docker
docker compose down          # 删掉旧网络,让 mtrip_default 按新 MTU 重建
docker network inspect bridge -f '{{index .Options "com.docker.network.driver.mtu"}}'   # 应为 1450
```

`daemon.json` 的 `mtu` 同时作用于**构建容器**和 compose 新建的网络,所以 build 与运行时一次解决。

## 8. 常见问题

**`permission denied: ./mtrip.sh`**
执行 `chmod +x deploy/mtrip.sh`。

**`未找到 docker compose`**
需要 Docker Engine 20.10+ 自带的 compose 插件(`docker compose version`),或独立的 `docker-compose`,脚本两者都兼容。

**`$'\r': command not found` / 报错行号乱跳**
文件被转成了 CRLF 换行。执行 `sed -i 's/\r$//' deploy/mtrip.sh` 修回 LF。

**`clean` 之后数据没了**
这是预期行为:`clean` = `docker compose down -v`,会删除 MySQL 数据卷,下次启动按 `database/` 下的 SQL 重新建表导种子。
只想删容器保数据用 `down`。

**build 报 `Your requirements could not be resolved` + `affected by security advisories`**
不是网络问题。仓库不提交 `composer.lock`(根 `.gitignore` 排除了 `backend/**/composer.lock`),
`composer install` 于是退化成 `update`,而 `update` 即使带 `--no-dev` 也要解析 `require-dev` 的依赖树,
撞上 Composer 新版的安全审计拦截(如 `hyperf/testing` → `phpunit ^10.0` 全系列被标记,无干净版本可选)。
Dockerfile 已加 `--no-security-blocking` 关掉解析期拦截 —— 带 `--no-dev` 时这些 dev 包本就不会装进镜像。
若想根治并获得可复现构建,需要生成并提交各服务的 `composer.lock`(会改动 `.gitignore` 约定,另行决策)。

**build 卡在 `composer install` 几分钟后超时**
见第 7.2 节:`deploy/.env` 里加 `COMPOSER_MIRROR=https://mirrors.aliyun.com/composer/`,重新 `./mtrip.sh build`。
注意 `.env` 是从旧模板复制的话不会自动带上这个键,得手工补。

**build 报 `failed to resolve reference "docker.io/..."`**
见第 7.1 节:镜像加速器地址已失效或 Docker 配置文件改错了位置(snap 版尤其容易踩)。

**改了 `.env` 不生效**
`.env` 是构建/启动时注入的环境变量,必须 `./mtrip.sh start`(会重建容器),`restart` 不重新读取。
验证注入结果:`docker exec mtrip-user-service-1 sh -c "env | grep MTRIP_"`。
