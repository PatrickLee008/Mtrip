# mtrip.sh 使用说明(服务启停脚本)

> 位置:`deploy/mtrip.sh` | 适用:Linux / macOS / Windows(Git Bash、WSL)
> 本脚本是 `deploy/README.md` 各场景 docker compose 命令的封装入口,两者语义一致。
> Windows PowerShell 原生环境请直接用 `deploy/README.md`;S7 验收栈的 PowerShell 版是 `scripts/s7-environment.ps1`。

## 0. 一分钟上手

```bash
cd deploy
chmod +x mtrip.sh          # 首次需要(从 Windows 拷来的仓库尤其注意)
./mtrip.sh build           # 首次:构建镜像 + 启动全部服务(分钟级)
./mtrip.sh health          # 验证:8 个微服务 + 网关探活
```

之后日常只需:

```bash
./mtrip.sh start                   # 启动
./mtrip.sh restart goods-service   # 改完 PHP 代码热重启(约 2 秒)
./mtrip.sh stop                    # 停止
```

脚本可从任意目录调用(内部自动 `cd` 到 `deploy/`),例如 `./deploy/mtrip.sh status`。
用 `./mtrip.sh` 或 `bash mtrip.sh` 都行;即使写成 `sh mtrip.sh`,脚本首行也会自动改用 bash 重新执行。

## 1. 命令一览

| 命令 | 等价 docker compose | 说明 |
| --- | --- | --- |
| `start [服务名...]` | `up -d` | 启动,不重建镜像;缺 `.env` 时自动从 `.env.example` 生成 |
| `build [服务名...]` | `up -d --build` | 重建镜像并启动;改 Dockerfile / 新增 composer 依赖时用 |
| `restart [服务名...]` | `restart` | 热重启;只改 PHP 代码时用,约 2 秒/个 |
| `stop [服务名...]` | `stop` | 停止容器,保留容器与数据 |
| `down` | `down` | 删除容器与网络,**保留数据卷**(数据不丢) |
| `clean` | `down -v` | 删除容器与数据卷(**数据库清空**,需输入 `yes` 确认) |
| `status` / `ps` | `ps` | 容器状态 |
| `logs [服务名...]` | `logs -f --tail=100` | 跟踪日志,Ctrl+C 退出 |
| `health` | — | 8 个微服务 healthz + 网关链路探活,全通过退 0、有失败退 1 |
| `help` | — | 帮助 |

可用服务名(不传 = 全部;传了未知名直接报错退出,防拼写错误静默失败):

```
system-service  user-service   goods-service     order-service
merchant-service finance-service marketing-service payment-service
mysql  redis  gateway
```

环境变量 `MTRIP_YES=1` 可让 `clean` 跳过交互确认(CI / 脚本化重建用,慎用)。

## 2. 三种栈模式

| 模式 | 加载的 compose 文件 | project | 网关 | 用途 |
| --- | --- | --- | --- | --- |
| 默认 | `docker-compose.yml` + `docker-compose.override.yml` | `mtrip` | `:8081` | 日常开发,本地源码热挂载 |
| `--prod` | 只 `docker-compose.yml` | `mtrip` | `:8081` | 不挂本地源码,改代码必须 `build` |
| `--s7` | `docker-compose.yml` + `docker-compose.s7.yml` | `mtrip-s7` | `127.0.0.1:8181` | 隔离验收环境 |

模式开关放在任意位置都行:`./mtrip.sh start --s7` 与 `./mtrip.sh --s7 start` 等价。

### S7 隔离验收栈(等价 `scripts/s7-environment.ps1`)

```bash
./mtrip.sh start --s7      # 启动(up -d --no-build --pull never,串行)
./mtrip.sh health --s7     # 容器内逐个探活 + 网关探活
./mtrip.sh status --s7
./mtrip.sh stop --s7       # 只停,保留卷与验收留痕
```

与开发栈的关键差异,都是设计使然:

- **绝不加载 `docker-compose.override.yml` 和开发者的 `.env`**,改用 `s7.env.example`,保证验收环境不受本地改动污染;
- **只用已构建好的镜像**(`--no-build --pull never`),镜像缺失即失败 —— 所以 `./mtrip.sh build --s7` 会被脚本直接拒绝,请先在默认栈 `./mtrip.sh build` 产出 `mtrip-*-service:latest`;
- 源码以**只读**方式挂载,`WORKER_NUM=1`,业务服务与数据库**端口一律不对外发布**,只有网关绑定 `127.0.0.1:8181`;
- 因此 `health --s7` 不能用宿主机 curl,改为 `docker exec` 进容器探 `127.0.0.1:<端口>/healthz`(每个服务最多等 40 秒),与 PowerShell 版同法;
- 网关刷新用 `nginx -s reload` 而非 `restart`,不中断已建立的验收会话;
- `stop --s7` 只停容器、保留 `s7-uploads` 卷(验收留痕不自动删)。

## 3. 按场景选命令(勿一律 build)

| 场景 | 命令 | 耗时 |
| --- | --- | --- |
| 只改 PHP 代码(`app/`、`config/`、`backend/shared/src`) | `./mtrip.sh restart goods-service` | ~2 秒 |
| 改了 `docker-compose.yml` / `.env` 环境变量 | `./mtrip.sh start` | ~10 秒 |
| 新增 composer 依赖 / 改 Dockerfile | `./mtrip.sh build user-service` | 分钟级 |
| 改了网关路由 `openresty/conf.d/mtrip.conf` | `./mtrip.sh restart gateway` | ~2 秒 |
| 新增/修改数据库 SQL | 优先 `scripts/db-apply.ps1`(幂等增量,不必清库) | 秒级 |
| 确实要清库重来 | `./mtrip.sh clean; ./mtrip.sh build` | 分钟级 |

热重启原理:`docker-compose.override.yml` 把本地 `app/`、`config/`、`backend/shared/src` 挂进容器覆盖镜像内代码,
`restart` 后 Hyperf 重新扫描即生效,不需要重建镜像。`--prod` / `--s7` 模式不挂载,改代码必须重新 `build`。

**新增 SQL 文件时注意**:`docker-compose.yml` 的 mysql `volumes` 段逐条列出了所有 initdb 挂载,
新加的 SQL 必须登记进去,否则只对 `db-apply` 生效,清库重建时会漏执行。

## 4. 脚本替你处理的三件事

1. **自动生成 `.env`** —— `start` / `build` 发现 `deploy/.env` 不存在时自动 `cp .env.example .env` 并告警。
   生产环境务必手改其中的 `MYSQL_*` 密码与 `MTRIP_JWT_SECRET` / `MTRIP_AES_KEY` / `MTRIP_ADMIN_AES_KEY`。
   (`--s7` 模式不碰开发者 `.env`。)
2. **自动建 `deploy/uploads/`** —— merchant-service 写入、gateway 只读挂载的共享目录。不预建的话
   Docker 会以 root 属主自动创建,后续容器内写文件容易踩权限问题。该目录已被 `deploy/.gitignore` 忽略。
3. **自动刷新网关** —— `start` / `build` 重建业务容器后 IP 会变,而 OpenResty 启动时就解析并缓存了上游 IP,
   表现为「服务 healthz 正常但网关全部 502」。脚本在 `up` 之后自动重启(S7 下是 reload)网关规避。
   `restart xxx-service` 不换 IP,脚本也就不会多此一举动网关。

## 5. 启动后的入口

| 入口 | 地址 | 备注 |
| --- | --- | --- |
| 网关(admin/app/merchant/supplier 统一入口) | http://localhost:8081 | 取 `.env` 的 `GATEWAY_HOST_PORT` |
| 微服务直连 healthz | 9501~9508 | system/user/goods/order/merchant/finance/marketing/payment |
| 前端静态站 | 8090 / 8091 / 8092 / 8093 | admin / merchant / supplier / **client(H5)**,产物在 `deploy/web/<名>/`,端口取 `.env` 的 `*_WEB_PORT`;宝塔建站场景见 `README.md` 第 7 节 |
| MySQL | localhost:3307 | `MYSQL_HOST_PORT`,账号见 `.env` |
| Redis | localhost:6380 | `REDIS_HOST_PORT` |
| 上传文件 | `deploy/uploads/` | 经网关 `/uploads/` 静态访问 |
| S7 网关 | http://127.0.0.1:8181 | 仅本机;其余端口一律不发布 |

`start` / `build` 成功后脚本会打印上述入口(端口值实时从对应 env 文件读取)。

## 6. health 命令读法

```bash
./mtrip.sh health          # 开发/prod 栈
./mtrip.sh health --s7     # 验收栈
```

- 8 个微服务 `/healthz` 期望 **200**(S7 下是容器内探测,输出 `OK`);
- 网关 `/healthz` 期望 **200**;
- 网关转发 `POST /api/v1/app/auth/login`(不带签名头)期望 **401** —— 说明转发链路与签名中间件都正常;
  返回 **502** 表示上游不可达,跑 `./mtrip.sh restart gateway`;
- 全通过退出码 0,有失败退出码 1,可直接用作部署后门禁。

刚 `build` 完容器需要 10~30 秒预热,首次失败先等一会儿重试;持续失败用 `./mtrip.sh logs <服务名>` 看日志。

## 7. 日志

- 文件日志挂载在 `deploy/logs/<服务名>/`:`hyperf.log`(异常,按天滚动)、
  `request.log`(全量请求,需 `.env` 设 `MTRIP_REQUEST_LOG=true`);
- 容器实时输出:`./mtrip.sh logs order-service`。

## 8. 国内网络:两处要换源

`build` 会拉两类东西,换源位置不同,别混。

### 8.1 Docker 镜像(mysql / redis / openresty / hyperf 基础镜像)

配置文件位置取决于安装方式,**snap 版不读 `/etc/docker/daemon.json`**:

| 安装方式 | 配置文件 | 重启命令 |
| --- | --- | --- |
| apt / deb | `/etc/docker/daemon.json` | `systemctl restart docker` |
| snap | `/var/snap/docker/current/config/daemon.json` | `snap restart docker` |

`ps -ef | grep dockerd` 看 `--config-file=` 参数即可确认。改完用
`docker info | grep -A4 "Registry Mirrors"` 确认生效。

### 8.2 云主机必查:docker0 与出口网卡的 MTU 不一致

换源换对了仍然 `curl error 28 ... Connection timed out`,比一眼 MTU:

```bash
cat /sys/class/net/docker0/mtu     # Docker 网桥,默认 1500
ip route show default               # 找出出口网卡名,如 ens10
cat /sys/class/net/ens10/mtu       # 云主机常见 1450
```

**出口网卡 < 1500 就必须给 Docker 设同样的 MTU**(`daemon.json` 加 `"mtu": 1450`,重启 daemon,
再 `docker compose down` 让网络按新 MTU 重建)。否则容器按 1500 发包,超出部分要靠 ICMP
"fragmentation needed" 做路径 MTU 发现,而云厂商安全组普遍丢弃这类 ICMP,形成 **MTU 黑洞**:

- 小包正常 → composer 元数据能拉到,进度条能动;
- 大包(TLS 证书、`packages.json`、dist 压缩包)全部卡满超时 → `curl error 28`;
- 宿主机 `curl` 同一地址却秒开(宿主机走的就是 1450),**极易误判成"源不可用"而反复换源**。

`daemon.json` 的 `mtu` 同时作用于构建容器与 compose 新建的网络,build 与运行时一次解决。

## 9. 常见问题

**`permission denied: ./mtrip.sh`**
执行 `chmod +x deploy/mtrip.sh`。

**`未找到 docker compose`**
需要 Docker Engine 自带的 compose 插件(`docker compose version`)或独立 `docker-compose`,脚本两者都兼容。

**`$'\r': command not found` / 报错行号乱跳**
文件被转成了 CRLF 换行。执行 `sed -i 's/\r$//' deploy/mtrip.sh` 修回 LF。

**`./mtrip.sh build --s7` 被拒绝**
不是 bug。S7 按设计只跑预构建镜像,先在默认栈 `./mtrip.sh build` 产出 `mtrip-*-service:latest`,再 `./mtrip.sh start --s7`。

**S7 启动报镜像不存在**
同上,`--pull never` 不会去拉镜像。先在默认栈构建。

**`clean` 之后数据没了**
预期行为:`clean` = `down -v`,会删数据卷,下次启动按 `database/` 下的 SQL 重新建表导种子。
只想删容器保数据用 `down`。

**改了 `.env` 不生效**
`.env` 在启动时注入,必须 `./mtrip.sh start`(会重建容器),`restart` 不重新读取。
验证:`docker exec mtrip-user-service-1 sh -c "env | grep MTRIP_"`。
